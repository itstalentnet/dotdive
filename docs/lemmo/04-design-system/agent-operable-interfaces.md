# اصول رابط کاربری قابل‌استفاده برای عامل‌های هوش مصنوعی
## Agent-Operable Interfaces — زاویه‌ی پنجم: وقتی «کاربر» یک مدل هوش مصنوعی است، نه فقط یک انسان

> **زنجیره پنج‌گانه تصمیم‌گیری در دیزاین سیستم Lemmo:**  
> - **زاویه اول ([DOC-DS-007](./design-decision-principles.md)):** فاصله‌گذاری مبتنی بر رابطه، تایپوگرافی، پالت معنایی رنگ و بودجه موشن.  
> - **زاویه دوم ([DOC-DS-008](./container-relationship-and-inheritance.md)):** معماری وراثت در کانتینرها، رادیوس هم‌مرکز و همگام‌سازی چگالی والد-فرزند.  
> - **زاویه سوم ([DOC-DS-009](./responsive-decision-principles.md)):** چیدمان الگوریتمی و ترکیبی، گرید پازلی، تطبیق تصاویر و ناوبری واکنش‌گرا.  
> - **زاویه چهارم ([DOC-DS-010](./assistive-technology-and-microstates.md)):** فناوری‌های کمکی، استاندارد WCAG 1.4.13، حالت‌های اسکلتون/اسپینر و اتصال خطاهای فرم.  
> - **زاویه پنجم (این سند — DOC-DS-011):** رابط‌های قابل‌عملیات برای عامل‌های هوش مصنوعی (Agent-Operable Interfaces)، درخت دسترس‌پذیری، سه‌گانه Name/Role/Value، استاندارد WebMCP و سلکتورهای پایدار.

> **نکته‌ی کلیدی که کل این سند حول آن می‌چرخد:**  
> زیرساخت فنی که عامل‌های هوش مصنوعی برای «دیدن» و «کلیک‌کردن» روی یک صفحه استفاده می‌کنند، **همان درخت دسترس‌پذیری (Accessibility Tree)** است که دهه‌ها برای صفحه‌خوان‌های کاربران کم‌بینا ساخته شده است.  
> یعنی سند شماره‌ی چهار ([DOC-DS-010](./assistive-technology-and-microstates.md)) و این سند دو روی یک سکه‌اند — هر رابطی که برای یک کاربر نابینا درست کار کند، پایه‌ای بسیار محکم برای یک عامل هوش مصنوعی خواهد بود. مستندات رسمی چارچوب **Playwright** (پایه ابزارهای اتوماسیون مرورگر برای مدل‌های هوش مصنوعی) صراحتاً بیان می‌کند: عامل‌ها به‌جای پردازش سنگین اسکرین‌شات یا HTML خام، از **اسنپ‌شات درخت دسترس‌پذیری** استفاده می‌کنند.

## ۱. چرا Accessibility Tree زبان مشترک انسان و هوش مصنوعی است

### ۱.۱ چطور کار می‌کند
هر مرورگری، مستقل از ظاهر بصری صفحه، یک نمایش ساختاریافته از صفحه می‌سازد که هر دکمه، لینک، اینپوت و تیتر را با **نقش (role)**، **نام (name)** و **وضعیت (state)** آن مشخص می‌کند — مثلاً `Role: button, Name: ثبت سفارش, State: enabled`. این همان چیزی‌ست که صفحه‌خوان‌ها می‌خوانند، و امروز ابزارهای اتوماسیون هوش مصنوعی (مانند Playwright MCP که مایکروسافت آن را برای اتصال مدل‌های زبانی به مرورگر ساخته) دقیقاً همین درخت را — نه پیکسل‌ها و نه کدهای خام درهم‌تنیده HTML — به مدل زبانی ارائه می‌دهند.

### ۱.۲ مزایای درخت دسترس‌پذیری نسبت به اسکرین‌شات و HTML خام
- **کاهش چشمگیر مصرف کانتکست:** یک اسنپ‌شات دسترس‌پذیری معمولاً ۲ تا ۵ کیلوبایت است در مقابل ۱۰۰+ کیلوبایت برای اسکرین‌شات معادل — یعنی ۲۰ تا ۵۰ برابر بهینه‌تر از نظر مصرف پنجره کانتکست و هزینه توکن مدل.
- **استقلال از کلاس‌های CSS و جزئیات ظاهری:** عنصر با `Role: button, Name: Submit` شناسایی می‌شود؛ فرقی نمی‌کند کلاس CSS آن `btn-primary` باشد یا یک نام هش‌شده تصادفی مثل `xK7_submit_v3`. اگر ظاهر بصری صفحه تغییر کند ولی معنای عنصر حفظ شود، عامل هوش مصنوعی بدون شکست آن را می‌یابد.
- **پردازش مستقیم متنی:** برخلاف اسکرین‌شات، این روش نیازی به لایه پردازش بینایی سنگین و مستعد خطای پیکسلی ندارد و مستقیماً توسط مدل‌های زبانی قابل‌استدلال است.

> 🚨 **نتیجه‌ی عملی برای طراحی UI:** هر چیزی که ساختار دسترس‌پذیری صفحه را ضعیف کند (استفاده از `<div>` به‌جای عناصر معنایی، عدم تعریف role/name برای کامپوننت‌های سفارشی، وابستگی صرف به رنگ برای انتقال معنا) دقیقاً به همان اندازه که برای یک کاربر کم‌بینا مانع ایجاد می‌کند، عامل هوش مصنوعی را نیز از کار می‌اندازد.

## ۲. WAI-ARIA: نقش، نام، مقدار — زبان رسمی توصیف عناصر

### ۲.۱ سه‌گانه‌ی اجباری (WCAG 4.1.2 — Name, Role, Value)
طبق استاندارد رسمی W3C، هر کامپوننت رابط کاربری باید سه مولفه را **به‌صورت برنامه‌نویسی‌شده (programmatically determinable)** در دسترس قرار دهد:
- **Name (نام):** این عنصر چیست؟ («دکمه‌ی افزودن به سبد خرید»)
- **Role (نقش):** این عنصر چه نوع کنترلی است؟ (دکمه، چک‌باکس، اسلایدر، تب)
- **Value/State (مقدار/وضعیت):** وضعیت فعلی‌اش چیست؟ (انتخاب‌شده، غیرفعال، بازشده، مقدار عددی یک اسلایدر)

اگر این سه‌گانه به‌درستی تعریف نشوند، نه صفحه‌خوان و نه عامل هوش مصنوعی متوجه ماهیت کنترل نخواهند شد.

### ۲.۲ قانون طلایی: اول HTML معنایی، سپس ARIA
طبق راهنمای رسمی W3C ARIA Authoring Practices Guide (APG): اگر یک عنصر HTML بومی (`<button>`, `<input>`, `<a href>`) همان کارکرد را پوشش می‌دهد، همواره آن را به یک `<div>` با اتریبیوت‌های دستی ARIA ترجیح دهید. عناصر بومی به صورت پیش‌فرض نقش، پشتیبانی کیبورد و رفتارهای استاندارد را دارند. ساخت یک `<div role="button">` تعهدی است که توسعه‌دهنده باید تمام رفتارهای کلید Tab، Enter و Space را دستی با جاوااسکریپت کدنویسی کند، در غیر این صورت این قول شکسته شده و عامل هوش مصنوعی گمراه می‌شود.

### ۲.۳ نقش‌های Landmark — نقشه‌ی راه صفحه برای عامل
عناصر معنایی (`<header>`, `<nav>`, `<main>`, `<footer>`, `<aside>`) یا نقش‌های معادل ARIA (`role="navigation"`, `role="main"`) به عامل اجازه می‌دهند بدون پویش کل درخت صفحه، مستقیماً به بخش مدنظر (مثلاً فرم اصلی یا نوار کناری) بپرد.

## ۳. فرم‌ها — پایه‌ی تعاملات عملیاتی عامل هوش مصنوعی

### ۳.۱ برچسب صریح و واژگان استاندارد `autocomplete`
- هر فیلد ورودی الزاماً باید دارای یک `<label for="...">` واقعی باشد تا هدف فیلد برای عامل بدون ابهام مشخص گردد.
- اتریبیوت رسمی `autocomplete` (استاندارد WHATWG HTML) یک **واژگان استاندارد ماشین‌خوان** برای هدف فیلدهاست (`given-name`, `email`, `tel`, `postal-code`, ...). طبق تکنیک W3C H98، این شناسه فارغ از اینکه لیبل بصری به چه زبانی نوشته شده است، هویت فیلد را برای عامل ماشین اثبات می‌کند.
- از غیرفعال‌سازی با `autocomplete="off"` به جز در موارد ضروری امنیتی (کدهای یک‌بارمصرف) اکیداً پرهیز کنید.

### ۳.۲ اعلام وضعیت کامپوننت‌های سفارشی
المان‌های سفارشی (مانند تب‌ها، آکاردئون‌ها، منوهای کشویی) باید وضعیت باز/بسته یا فعال بودن خود را با ویژگی‌های ARIA بازتاب دهند:
- `aria-expanded="true/false"` برای باز یا بسته بودن منوها و آکاردئون‌ها.
- `aria-selected="true/false"` برای نشان دادن تب یا گزینه انتخاب‌شده.
- `aria-checked="true/false"` برای چک‌باکس‌ها و سوییچ‌های اختصاصی.  
بدون این خصوصیات، عامل هوش مصنوعی نمی‌داند در حال حاضر منو باز است یا بسته، و ممکن است روی عنصری کلیک کند که باز نیست.

## ۴. WebMCP — استاندارد نوین تبادل مستقیم صفحه با عامل هوش مصنوعی

### ۴.۱ مفهوم WebMCP (Web Model Context Protocol)
فراتر از استنباط غیرمستقیم صفحه از طریق درخت دسترس‌پذیری، استاندارد در حال تکوین **WebMCP** توسط کارگروه W3C Web Machine Learning و با مشارکت مستقیم مهندسان Chrome (Google) و Edge (Microsoft) در حال توسعه است.  
در این الگو، وب‌سایت به جای منتظر ماندن برای حدس زدن عامل، قابلیت‌های تعاملی خود را از طریق یک API بومی مرورگر (`navigator.modelContext`) به صورت ابزارهای صریح (Tools) رجیستر می‌کند:

```javascript
navigator.modelContext.registerTool({
  name: "search_flights",
  description: "جستجوی پروازهای موجود بین دو فرودگاه در یک تاریخ مشخص",
  inputSchema: {
    type: "object",
    properties: {
      origin: { type: "string", description: "کد فرودگاه مبدا" },
      destination: { type: "string", description: "کد فرودگاه مقصد" },
      date: { type: "string", description: "تاریخ سفر به فرمت YYYY-MM-DD" }
    },
    required: ["origin", "destination", "date"]
  },
  execute: async ({ origin, destination, date }) => {
    const flights = await fetchFlights(origin, destination, date);
    return { results: flights };
  }
});
```

### ۴.۲ وضعیت فعلی و رویکرد مهندسی Lemmo
این استاندارد در مرحله Draft Community Group قرار دارد. بهترین اقدام در معماری فعلی فرانت‌اند، **جداسازی کامل منطق بیزنس و هوک‌های عملیاتی از کامپوننت‌های رندرینگ UI** است. در این صورت، در آینده می‌توان این ابزارها را بدون بازنویسی رابط کاربری، مستقیماً روی توابع موجود سوار کرد.

### ۴.۳ رابطه تکمیلی ARIA و WebMCP
ARIA به عامل می‌گوید: *«این یک دکمه است و این نام آن است»*؛ WebMCP می‌گوید: *«این یک قابلیت سیستمی با این ورودی‌های ساختاریافته است»*. بهترین معماری هر دو را به صورت همزمان حفظ می‌کند: **ARIA برای تمامی عامل‌های مبتنی بر اتوماسیون مرورگر، و WebMCP برای عامل‌های مجهز به فراخوانی مستقیم پروتکل.**

## ۵. سلکتورهای پایدار — مکان‌یابی قابل‌اتکا برای عامل و تست خودکار

### ۵.۱ اولویت سلکتورها بر اساس استاندارد رسمی Playwright
چارچوب Playwright اکیداً توصیه می‌کند که عناصر بر اساس **آنچه کاربر می‌بیند و تجربه می‌کند** مکان‌یابی شوند، نه ساختار پیاده‌سازی داخلی:

| اولویت | نوع سلکتور | نمونه کد Playwright | مزیت معماری |
|---|---|---|---|
| **۱ (بهترین)** | نقش + نام دسترس‌پذیر | `getByRole('button', { name: 'ارسال' })` | پایدار در برابر تغییر فریم‌ورک و استایل |
| **۲** | برچسب متنی مرتبط | `getByLabel('ایمیل')` | منطبق بر ساختار فرم‌های دسترس‌پذیر |
| **۳** | پلیس‌هولدر (در صورت فقدان لیبل) | `getByPlaceholder('جستجو...')` | روش جایگزین موقت |
| **۴** | شناسه تست اختصاصی پایدار | `getByTestId('checkout-submit')` | پایدار در کامپوننت‌های پیچیده کانواس |
| **۵ (ممنوع)** | سلکتورهای CSS شکننده | `div.btn-primary-v3_final` | شکننده و وابسته به کامپایلر استایل |

> 🚫 کلاس‌های CSS کامپایل‌شده (مانند کلاس‌های تصادفی Styled-Components یا ماژول‌های CSS) هرگز نباید تنها راه دستیابی به یک عنصر باشند.

## ۶. انتظار و مدیریت مسابقه (Auto-Waiting & Race Conditions)

### ۶.۱ پیشگیری از Race Condition بین عامل و صفحه
اگر عامل بلافاصله پس از کلیک روی دکمه‌ای که درخواست ناهمگام (Async) می‌فرستد گام بعدی را بردارد، روی صفحه‌ای که هنوز در حال پردازش است کلیک خواهد کرد. ابزارهای اتوماسیون مدرن به صورت پیش‌فرض از مکانیزم **Auto-Waiting** استفاده می‌کنند؛ یعنی قبل از هر اقدام مطمئن می‌شوند که عنصر:
1. در درخت DOM حاضر است.
2. قابل مشاهده (Visible) است.
3. پایدار است (انیمیشن آن به پایان رسیده).
4. فعال (Enabled) است.

### ۶.۲ نقش سیگنال‌های DOM در هدایت عامل
- همان خصوصیات `aria-busy="true"` و `aria-live` که در سند [DOC-DS-010](./assistive-technology-and-microstates.md) تعریف شد، سیگنال رسمی اعلام وضعیت پردازش به عامل هوش مصنوعی است.
- دکمه‌ای که پردازش ناهمگام را آغاز می‌کند باید در طول عملیات `aria-disabled="true"` شود یا نام آن موقتاً به «در حال پردازش...» تغییر یابد تا عامل روی آن کلیک تکراری نکند.
- از انیمیشن‌های بی‌پایان که وضعیت قطعی پایان را منعکس نمی‌کنند باید پرهیز شود.

## ۷. انعکاس خطاها از دید عامل هوش مصنوعی

عامل هوش مصنوعی برای درک شکست عملیات از ساختار درختی استفاده می‌کند:
- اتریبیوت `aria-invalid="true"` روی فیلد، نامعتبر بودن ورودی را فوراً به عامل گزارش می‌دهد.
- اتریبیوت `role="alert"` باعث می‌شود پیام خطا بلافاصله در اسنپ‌شات دسترس‌پذیری منعکس شود.
- **خطاهای صرفاً بصری (مانند یک کادر قرمز بدون متن ساختاریافته) برای عامل هوش مصنوعی کاملاً نامرئی هستند.** عامل رنگ پیکسل‌ها را بررسی نمی‌کند، مگر با پردازش بینایی که بسیار پرهزینه‌تر و کم‌دقت‌تر است.

## ۸. سناریوی عملی: «کاربر از هوش مصنوعی می‌خواهد تصویری در استودیو تولید کند»

یک سناریوی کامل تعامل عامل با رابط کاربری در Lemmo Studio:
1. **یافتن فیلد پرامپت:** مکان‌یابی `<textarea>` با نام دسترس‌پذیر «توضیح پرامپت تصویر».
2. **درج ورودی:** وارد کردن متن دستور توسط عامل در فیلد.
3. **کلیک روی دکمه اکشن:** کلیک روی دکمه با نقش `button` و نام «تولید تصویر».
4. **تشخیص وضعیت بارگذاری:** دکمه به `aria-busy="true"` تغییر وضعیت داده و اسکلتون کانتینر در DOM فعال می‌شود؛ عامل منتظر پایان می‌ماند.
5. **دریافت و تحلیل نتیجه:** تصویر تولیدشده در ناحیه‌ای با `aria-live="polite"` قرار گرفته و متن `alt` توصیفی آن به عامل امکان می‌دهد نتیجه را درک کند.
6. **مدیریت خطای احتمالی:** در صورت بروز خطا، پیام ساختاریافته با `role="alert"` علت را اعلام کرده و عامل می‌تواند پرامپت را اصلاح یا کاربر را مطلع سازد.

## ۹. چک‌لیست خودارزیابی رابط دوستدار عامل (Agent-Ready Checklist)

- [ ] آیا تمام دکمه‌ها و لینک‌ها دارای Role و Name معنادار در درخت دسترس‌پذیری هستند؟
- [ ] آیا به جای `div`های سفارشی از عناصر معنایی بومی (`<button>`, `<input>`, `<a>`) استفاده شده است؟
- [ ] آیا وضعیت منوها، دراورها و تب‌ها با `aria-expanded` و `aria-selected` اعلام می‌شود؟
- [ ] آیا تمام اینپوت‌ها دارای تگ `<label>` متناظر و اتریبیوت استاندارد `autocomplete` هستند؟
- [ ] آیا در تست‌ها و سلکتورها اولویت با `getByRole` و `getByLabel` است و از کلاس‌های شکننده اجتناب شده؟
- [ ] آیا بخش‌های کلیدی اپلیکیشن دارای Landmarkهای معنایی (`<nav>`, `<main>`, `<aside>`) هستند؟

## منابع پژوهشی این سند
- **Playwright (Microsoft)** — مستندات رسمی اتوماسیون با اسنپ‌شات Accessibility Tree و ابزار Playwright MCP
- **Playwright Best Practices** — راهنمای انتخاب سلکتورهای مقاوم (`getByRole`, `getByLabel`, `getByTestId`)
- **W3C WAI-ARIA 1.2 / 1.3** — مشخصات رسمی نقش‌ها، حالات و خواص در دسترس‌پذیری وب
- **W3C ARIA Authoring Practices Guide (APG)** — الگوهای استاندارد ساخت ویجت‌های تعاملی
- **WCAG 4.1.2** — اصل Name, Role, Value در هدایت عناصر تعاملی
- **WHATWG HTML Standard** — مشخصات فنی اتریبیوت `autocomplete` و تکنیک W3C H98
- **W3C Web Machine Learning Community Group** — پیش‌نویس استاندارد **WebMCP** (`navigator.modelContext`)
- **Anthropic Model Context Protocol (MCP)** — استانداردهای ارتباط کلاینت با عامل‌های هوشمند
