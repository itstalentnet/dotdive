# آمادگی عملیاتی MVP؛ تکمیل پیشنهاد مشاور

## ۱. تصمیم دامنه و اعتبار این بررسی

هدف مالک محصول، لانچ اولیه با زیرساخت قابل مشاهده و قابل اداره است. رفع همه باگ‌های پیچیده، بازطراحی سرویس‌ها و بلوغ کامل سیستم توزیع‌شده به بعد از MVP موکول می‌شود. راهبرد مصوب اجرایی در [نقشه راه بک‌اند](./roadmap.md) حفظ می‌شود؛ این سند جزئیات پیشنهادی برای بریف‌های STB-05 تا STB-10 است، نه ADR مصوب، نه مجوز انتشار و نه گزارش پذیرش.

بررسی 2026-10-15 بر فایل‌های فعلی ورک‌تری انجام شد. `api/` و `dotdive/` تغییرات staged و unstaged قبلی دارند. شواهد زیر درباره سورس‌اند؛ هویت image مستقر، وضعیت سرویس‌های زنده و سلامت مسیر کاربر در این دور بررسی نشده است. هیچ فرمان مالی، تولید پولی، restart، migration یا تست اختلال اجرا نشد.

## ۳. حداقل مشترک لاگ، شناسه و خطا

پیاده‌سازی پیشنهادی در core و adapterهای فعلی؛ rollout نخست فقط سرویس‌هایی که واقعاً در مسیر منتخب ورود→دسترسی→اعتبار→تولید تصویر→ذخیره→تاریخچه فراخوانی می‌شوند. فهرست نهایی از مسیر اجرایی استخراج شود، نه از فهرست همه سرویس‌های repo.

- JSON در stdout با زمان UTC، level، service، نسخه/instance، operation، outcome، duration و شناسه درخواست/trace. رویداد آغاز، پایان و شکست مرزهای سرویس کافی است؛ لاگ همه توابع لازم نیست.
- `trace_id` برای اتصال زنجیره؛ `request_id` برای درخواست ورودی؛ `job_id`، `event_id`، `attempt_id` و شناسه عملیات مالی برای عملیات پایدار مربوط. این شناسه‌ها جایگزین کلید idempotency نمی‌شوند. retry یک event هویت همان event را حفظ کند.
- انتقال context از HTTP به gRPC خروجی، outbox ذخیره‌شده، header پیام و consumer؛ پس از restart/replay باید اتصال به Job باقی بماند. از انتقال صرف در context حافظه نتیجه دوام نگیریم. مهاجرت سراسری ستون همه جدول‌ها شرط MVP نیست.
- استفاده از propagator معتبر برای traceparent؛ ورودی نامعتبر/بیش‌ازحد طولانی نرمال شود. هدر trace هویت امنیتی نیست. معنای header قدیمی و شناسه‌ای که UI کپی می‌کند پیش از تغییر قرارداد مشخص شود؛ سازگاری کلاینت فعلی حفظ شود.
- reason/domain/status و شناسه پیگیری از سرویس تا SDK/UI حفظ شوند؛ مطابق [قرارداد خطای موجود](./style-guide.md) از reason برای ترجمه استفاده شود. خطای ناشناخته پیام امن و کد پیگیری بدهد. قطع SSE بعد از ارسال header نیز باید در وضعیت نهایی پیام/Job قابل مشاهده باشد.
- credential، cookie، token، prompt، invite code، URL امضاشده و body خام در لاگ یا فایل شواهد نباشند. شناسه‌های کاربر/ورک‌اسپیس فقط مطابق سیاست داده پروژه و نیاز عملیاتی ثبت شوند. error خامِ کتابخانه نیز بازبینی شود.
- collector اختیاری است؛ قطع export نباید درخواست را متوقف کند. اگر export اضافه شد، buffer محدود و رفتار drop مشخص داشته باشد. راه‌حل اولیه با stdout و جمع‌آوری محلی کافی است؛ نصب Jaeger یا dashboard شرط لانچ نیست.

## ۴. سه سطح سلامت؛ سه ادعای متفاوت

| سطح | چیزی که واقعاً اثبات می‌کند | شرط خروجی |
| --- | --- | --- |
| Liveness | پردازش/handler پاسخ می‌دهد | بدون وابستگی به Provider یا زنجیره کامل سرویس‌ها؛ جلوگیری از restart دسته‌جمعی هنگام قطعی یک وابستگی |
| Readiness | همین instance برای قابلیت منتخب وابستگی‌های ضروری را در اختیار دارد | بررسی محدود به timeout و وابستگی ضروری؛ failure پاسخ غیرموفق؛ اختلال وابستگی اختیاری جدا گزارش شود |
| Journey | کاربر مجاز روی نسخه مشخص عملیات واقعی را کامل کرده است | از Gateway، با بررسی نتیجه ذخیره‌شده و خطای قابل پیگیری؛ صرف ۲۰۰ یا ایجاد Job کافی نیست |

Readiness از recursion میان سرویس‌ها و فراخوانی پولی Provider دور بماند. برای worker، اتصال broker و فعال‌بودن consumer اهمیت دارد؛ برای مسیر مالی، DB و پاسخ خواندنی لجر؛ برای Storage، دسترسی به منبع موردنیاز. تنظیم timeout، threshold و آدرس‌ها در config نسخه‌دار باشد. نبود workspace کاربر با خرابی readiness سرویس یکی نیست.

Doctor خروجی واقعی را نمایش می‌دهد؛ خودش چیزی را repair، seed، grant، replay یا restart نمی‌کند. timeout، نبود ابزار، دسترسی ناکافی و نسخه نامعلوم خروجی «بررسی ناقص» دارند، نه سبز.

## ۵. قرارداد پیشنهادی فرمان‌های عملیاتی

**فرمان‌های این بخش هدف پیاده‌سازی‌اند؛ اکنون در Makefile موجود نیستند.** Make فقط ورودی ساده اپراتور است؛ backend runner باید به سرویس زنده متصل شود. runnerهای راستی‌آزمایی طبق قواعد پروژه در `tests/live/` یا `tests/e2e/` قرار می‌گیرند، نه `cmd/`. نام پوشه به معنی اجرای in-process یا mock نیست. تست واحد و CI موجود حذف نمی‌شوند.

| فرمان پیشنهادی | رفتار | اثر جانبی و خروجی |
| --- | --- | --- |
| `make doctor` | ابزارهای لازم، containerهای Created/Exited/restarting، نسخه image، readiness و وابستگی‌های مسیر منتخب | فقط‌خواندنی؛ جدول component/check/status/reason/duration و خروجی JSON پالایش‌شده |
| `make trace TRACE_ID=<id>` | جمع‌آوری محدود به زمان/حجم از log سرویس‌های همان محیط؛ اتصال event/job/attempt | فقط‌خواندنی؛ timeline تقریبی با مرزهای مفقود؛ نبود log مساوی نبود اجرای عملیات نیست |
| `make verify-journey` | کاربر آزمایشی مجاز، Gateway واقعی، دسترسی/اعتبار/تولید/asset/history | نوشتنی و احتمالاً پولی؛ تنها در محیط و سقف هزینه مجاز، با idempotency و fixture اختصاصی |
| `make release-check` | ترکیب doctor، نتیجه journey مرتبط با همان snapshot و شواهد بررسی مستقل | جمع‌بندی؛ به‌طور ضمنی journey پولی یا fault injection اجرا نکند؛ انتشار انجام نمی‌دهد |

پیشنهاد exit code برای runner: صفر یعنی همه بررسی‌های لازم موفق؛ ۱ یعنی شکست مشاهده‌شده؛ ۲ یعنی بررسی ناقص/پیش‌نیاز ناموجود. Make ممکن است کد غیرصفر را به کد شکست خودش تبدیل کند؛ CI بر موفق/ناموفق بودن Make و status دقیق فایل JSON تکیه کند. SKIP برای یک بررسی لازم هرگز PASS نیست.

برای هر اجرا: timestamp، محیط/profile، commit به‌همراه dirty بودن و patch fingerprint در صورت نیاز، image digest، نسخه config بدون مقادیر حساس، command، exit status، نتیجه هر check و شناسه‌های مرتبط ثبت شود. منبع شناسه‌ها و credential فایل امن محلی/نشست باشد؛ secret در آرگومان، history یا artifact نیاید. زمان و حجم log، retention و rotation قابل تنظیم باشد تا observability دیسک را پر نکند.

Trace محلی کل سیستم توزیع‌شده را با ترتیب قطعی اثبات نمی‌کند؛ اختلاف ساعت و لاگ گمشده صریح باشند. برای replay شناسه Job/event مرجع پایدار باقی می‌ماند.

## ۶. معیارهای خروج محدود پیش از لانچ

۱. **نسخه و دسترسی:** image/config اجراشده قابل شناسایی؛ مسیر اعتبار ناخواسته در Gateway و سرویس در دسترس عمومی نیست؛ درخواست ردشده اثر مالی ندارد. این بررسی هدفمند جای ممیزی جامع اعطاهای قدیمی نیست.

۲. **سلامت قابل اعتماد:** doctor روی مسیر منتخب اجرا شود؛ یک وابستگی ضروری از دسترس خارج شود و خروجی غیرسبز با علت روشن بدهد. اختلال فقط در محیط بررسی مجاز و ایزوله؛ بازگردانی وابستگی و پایان بررسی ثبت شود. endpoint ثابت UP پذیرفته نیست.

۳. **عملیات عادی:** یک journey کاربر تازه از Gateway، با اعتبار معتبر، تولید واقعی در سقف مجاز، ثبت و دریافت asset، بارگذاری دوباره تاریخچه و اثر مالی قابل تطبیق. مسیر بی‌هزینه می‌تواند بخش‌های دسترسی و خطا را بررسی کند ولی شاهد تولید واقعی نیست. نبود مجوز هزینه یعنی بخش تولید NOT RUN، نه پاس ساختگی.

۴. **شکست قابل تشخیص:** یک شکست کنترل‌شده در مسیر منتخب با همان شناسه در سرویس و UI قابل دنبال‌کردن باشد؛ کاربر در spinner بی‌پایان نماند. deadline و وضعیت نامعلوم صریح داشته باشد. نامعلوم‌بودن نتیجه Provider مجوز refund یا retry کور نیست؛ رفتار مالی مصوب حفظ شود. ساخت reaper عمومی یا پوشش همه crash windowها شرط این گام نیست.

۵. **عملیات روزمره:** فرمان trace محل آخرین مرحله مشاهده‌شده و شکاف‌ها را نشان دهد؛ راهنمای کوتاه توقف پذیرش درخواست جدید، بازیابی سرویس و نسخه قبلی موجود باشد. سلامت backup و امکان بازیابی حداقلی داده از شواهد موجود بررسی شود؛ rollback image جای rollback schema/data فرض نشود. disaster recovery جامع و بار طولانی به بدهی بعد از MVP می‌روند.

۶. **شواهد و تصمیم:** مجری و بازبین جدا؛ نتایج همین snapshot ثبت شوند. بررسی دامنه MVP با پذیرش کامل تسک‌های تاریخی یکی نیست. checklist باز و CI اجرا‌نشده همان‌طور باز بمانند. این سند هیچ قاعده انطباق را لغو نمی‌کند و هیچ تأیید لانچی صادر نمی‌کند.

## ۷. تقسیم کار در مسیر موجود STB

| بسته | خروجی کوچک | وابستگی و حد توقف |
| --- | --- | --- |
| STB-05/06 | core logging، انتقال trace در مرزهای واقعی و بررسی یک موفقیت/یک شکست | از core و outbox موجود؛ بدون rollout همه سرویس‌ها یا بازنویسی مالی |
| STB-07/08 | reason/domain/شناسه از سرویس تا SDK/UI و بررسی رفتار مرورگر | پس از قرارداد شناسه مشترک؛ مستقل از closure تاریخی مالی |
| STB-09/10 | doctor/trace و wrapperهای journey/release-check، شواهد نسخه لانچ | آغاز طراحی فرمان‌ها اکنون؛ پذیرش runtime پس از اتصال trace و خطا؛ فقط blocker واقعی اصلاح شود |
| STB-01..04 | بررسی هدفمند اصلاحات امنیت/مالی موجود | صرفاً اثر واقعی روی نسخه لانچ؛ توسعه افقی و ماتریس جامع ادامه نیابد |

فرمان‌های عملیاتی، جای «فقط تست in-process به عنوان شاهد محصول» را می‌گیرند؛ همان فرمان‌ها بعداً قابل اجرای خودکار در CI هستند. هزینه‌دارها در CI پیش‌فرض فعال نشوند. بریف اجرایی هر بسته باید از قالب اصلی checklist با تمام ردیف‌های U و برچسب‌های دامنه استفاده کند؛ این پیشنهاد فنی جای بریف نیست.

## ۸. تعویق آگاهانه و قواعد بازگشت

دفتر موجود `.task/active/STB_POST_MVP_DEBT.md` حفظ شود؛ برای هر باگ: شاهد و snapshot، اثر کاربری، محدودیت/راهکار فعلی، دامنه کاربران در معرض، مالک نقش، زمان بازبینی پس از MVP و trigger بازگشت ثبت شود. نقش پیشنهادی با فرد تخصیص‌یافته اشتباه نشود. تعویق به معنای رفع‌شدن یا تأیید مستقل نیست.

- ماتریس جامع crash/retry/DLQ، reconciler عمومی میان همه مخازن، load/chaos طولانی، dashboard و rollout سراسری پس از MVP؛ داده‌های مالی یا asset موجود خودسرانه اصلاح نشوند.
- codegen آفلاین پروژه جداست؛ اگر تغییر قرارداد همین مسیر به codegen وابسته شد، فقط همان مانع بررسی شود. نبود اتوماسیون کامل به‌تنهایی شروع trace را متوقف نمی‌کند.
- باگ پیچیده‌ای که یک قابلیت اختیاری را خراب می‌کند می‌تواند با غیرفعال‌سازی روشن همان قابلیت و تصمیم مالک محصول تعویق شود. باگ مسیر اصلی که اجازه تولید/ذخیره را نمی‌دهد یا اثر مالی/دسترسی نادرست مشاهده‌شده دارد، با شرح اثر برای تصمیم محدودسازی لانچ برگردد؛ صرف برچسب DEFERRED آن را سالم نمی‌کند.
- ادعای سوءاستفاده یا امنیت کامل از مرور سورس صادر نشود. نشانه واقعی exposure، اثر مالی نادرست، از دست‌رفتن خروجی یا restart-loop شرط بازگشت زودتر است.

پیشنهاد مشاور برای بتا فقط هنگام ثبت‌نام، تغییر مالک projection و خاموش‌کردن intent تصمیم‌های محصول/معماری مستقل‌اند. این دور آن‌ها را تصویب نمی‌کند؛ مسیر فعلی بتا و مالکیت در اسناد مربوط ملاک بررسی می‌مانند. برای tracing لازم نیست این تصمیم‌ها دوباره باز شوند.


## ۹. اعتبارسنجی همین تغییر مستندات

- بازسازی `llms.txt` با `python3 dotdive/docs/lemmo/scripts/generate-llms.py` موفق شد (۸۶ سند).
- `npm run content:check` در `dotdive/` با exit code 1 شکست خورد: slug تکراری `index` در اسناد موجود معماری/فرانت و خطای YAML در فایل موجود `beta-invitation-and-gift-ownership.md` که جدول متادیتا را میان delimiterهای frontmatter قرار داده است. این فایل در تغییرات قبلی ورک‌تری بود و در این دور اصلاح نشد.
- این نتیجه صرفاً اعتبارسنجی مستندات است؛ هیچ بررسی سلامت runtime یا پذیرش لانچ از آن نتیجه نمی‌شود.


## ۱۰. پوشش قابلیت‌های مکمل Reliability

موجودی تفصیلی recovery، idempotency، outbox/inbox، DLQ، breaker/isolation، audit، SLO/alerting و DR در [DOC-OPS-003](../07-devops/platform-reliability-observability.md) ثبت شد. این سند همچنان مرجع حداقل فرمان‌ها و trace/log پیش از MVP است؛ استک مرکزی و بازیابی جامع به بسته‌های پس از MVP در رودمپ منتقل شده‌اند.


## همگام‌سازی با ADR-022 — پیشنهاد ثبت‌شده

مرجع: [ADR-022](../01-architecture/decisions/ADR-022-platform-reliability-and-observability.md)، وضعیت **Draft / Proposed**؛ متن زیر پیشنهاد معماری است و ادعای تصویب جزئیات یا اجرای قابلیت‌ها نیست. جهت‌گیری قبلی مالک محصول درباره دامنه MVP محفوظ است.

۱. Observability قابلیت مشترک و خارج از مسیر تجاری است؛ سرویس واسط اجباری میان Gateway و سرویس‌ها ایجاد نمی‌شود. قطع collector نباید عملیات محصول را متوقف کند؛ export ناهمگام و منابع آن محدود باشند.

۲. trace/context در HTTP، gRPC، SSE، outbox و broker منتقل شود؛ شناسه پایدار Job/event/attempt برای بازیابی حفظ شود. trace جای idempotency یا هویت امنیتی نیست. لاگ JSON پالایش‌شده، reason/domain و کد پیگیری تا UI حفظ شوند.

۳. liveness، readiness وابستگی ضروری و journey واقعی سه ادعای مستقل‌اند. پاسخ ثابت UP، وجود کانتینر و موفقیت تست in-process به‌تنهایی سلامت محصول را ثابت نمی‌کنند. فرمان عملیاتی باید شکست و بررسی ناقص را غیرموفق گزارش کند.

۴. recovery در سرویس مالک باقی می‌ماند: Job مالک چرخه Job، Image مالک تعامل Provider و بازیابی خروجی، Quota مالک اثر مالی، Storage مالک Asset و Agent مالک چرخه پیام است؛ این مرزبندی مالکیت‌های مصوب ADR-018..020 را جابه‌جا نمی‌کند. timeout Provider شکست قطعی نیست و retry پولی کور مجاز نیست.

۵. timeout/retry budget، circuit breaker، idempotency و جداسازی ظرفیت در مرز فراخوانی اعمال شوند. آستانه‌ها در config نسخه‌دار باشند. وجود کلاس breaker یا صف DLQ جای اثبات اتصال به رفتار واقعی و replay امن را نمی‌گیرد.

۶. قبل از MVP حداقل trace/log/error، readiness صادقانه، doctor/trace و یک مسیر موفق و شکست قابل تشخیص در STB-05..10 هدف است. استک مرکزی، recovery جامع، bulkhead پیشرفته، audit گسترده و DR کامل در REL-01..05 پس از MVP پیگیری شوند؛ شاهد بازیابی حداقلی لانچ حذف نمی‌شود.

۷. تعویق باگ پیچیده، رفع‌شدن یا پذیرش کامل نیست؛ ریسک، محدودیت و شرط بازگشت ثبت شوند. اثر مشاهده‌شده بر امنیت، مالی یا مسیر اصلی برای تصمیم محدودسازی لانچ بازگردد. checklist، CI و بازبینی مستقل با این ADR دور زده نمی‌شوند.

۸. انتخاب Collector/backendها، عدد SLO، کانال اعلان و افراد مسئول از این تصمیم نتیجه نمی‌شود. audit پایدار امنیتی/مالی با telemetry قابل sampling/drop یکی نیست. این ADR مالک بتا/Promo را تعیین نمی‌کند و هیچ سرویس تجاری جدیدی تصویب نمی‌کند.


## تفکیک گیت تشخیص اولیه از پذیرش محصول — رودمپ نسخه ۵

طبق دستور مالک محصول در 2026-10-15، اول تشخیص‌پذیری، سپس تکمیل backend با مالکیت دائمی، سپس آماده‌سازی frontend و اتصال کامل انجام می‌شود. گیت مرحله اول روی یک مسیر موجود منتخب و شکست کنترل‌شده همان مسیر است؛ تکمیل دعوت/Claim/چت جدید پیش‌نیاز آن نیست. هر مسیر تازه استاندارد trace/log را هنگام توسعه می‌پذیرد؛ journey کامل مرورگر تا اثر مالی و ذخیره در مرحله اتصال بررسی می‌شود. STB-10 پذیرش نهایی محصول است و شروع تکمیل backend را مسدود نمی‌کند. متن قبلی درباره journey نهایی در این دامنه خوانده شود؛ این تفکیک حذف شواهد یا تصویب ضمنی جزئیات Draft نیست.
