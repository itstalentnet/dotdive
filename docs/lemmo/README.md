# مستندات مرجع پروژه Lemmo — منبع یگانه حقیقت (SSOT)

> **اصل طلایی (The Golden Rule):**  
> در کل اکوسیستم نرم‌افزاری Lemmo برای هر قانون معماری، مقدار دیزاین‌توکن و تصمیم فنی، **دقیقاً یک منبع موثق (Single Source of Truth)** وجود دارد. ثبت اطلاعات تکراری یا متناقض در چند سند ممنوع است. این مخزن (`docs/`) مرجع رسمی، الزام‌آور و معتبر برای تمامی اعضای تیم (توسعه‌دهندگان، طراحان و ایجنت‌های هوش مصنوعی) می‌باشد.
> 
> 🤖 **الزامات ایجنت‌های هوش مصنوعی:** کلیه مدل‌ها و ایجنت‌های توسعه پیش از ایجاد یا ویرایش هر سند، موظف به رعایت پروتکل توقف و قوانین ضدتضاد در سند [**`RULE.md`**](./RULE.md) (و راهنمای عملیاتی [**`AGENTS.md`**](./AGENTS.md)) هستند.

## 📌 قانون اجباری: جدول متادیتای بالای هر سند (Document Metadata Header)

برای خوانش سریع توسط انسان، جستجوی راحت موضوعی و **پارس خودکار توسط اسکریپت‌های هوش مصنوعی (LLMs)**، **تمام فایل‌های مستندات جدید باید در بالاترین سطر خود دارای یک جدول متادیتا باشند**.

### ساختار جدول متادیتا:
```markdown
| فیلد / Field | مقدار / Value |
| :--- | :--- |
| **Title (EN)** | [عنوان استاندارد انگلیسی سند] |
| **Title (FA)** | [عنوان رسمی فارسی سند] |
| **ID** | DOC-[CATEGORY]-[NUM] (مانند DOC-FE-001 یا DOC-ARCH-002) |
| **Category** | `architecture` \| `design-system` \| `branding` \| `frontend` \| `backend` \| `devops` \| `modules` \| `roadmap` |
| **Status** | `Draft` (پیش‌نویس) \| `Active` (فعال) \| `Approved` (تأییدشده) \| `Deprecated` (منسوخ) |
| **Owner** | [تیم یا شخص مسئول - مثلاً Frontend Team / @username] |
| **Last Updated** | YYYY-MM-DD (تاریخ میلادی آخرین تغییر) |
| **Summary (EN)** | [یک یا دو جمله خلاصه انگلیسی جهت استفاده در ایندکس و هوش مصنوعی] |
| **Summary (FA)** | [یک یا دو جمله خلاصه فارسی جهت درک سریع مخاطب] |
| **Tags** | `برچسب۱`, `برچسب۲`, `برچسب۳` |
```

> 💡 **نکته مهم:** حتماً از الگوی آماده در مسیر [`templates/DOCUMENT_TEMPLATE.md`](./templates/DOCUMENT_TEMPLATE.md) کپی کنید.

## ✍️ راهنمای گام‌به‌گام نگارش مستندات جدید (Authoring Standards)

توسعه‌دهندگان هنگام افزودن هرگونه مستند باید گام‌های زیر را رعایت نمایند:

### گام اول: انتخاب پوشه مناسب
- سند مربوط به چه حوزه‌ای است؟ مستندات را فقط در یکی از پوشه‌های استاندارد جدول فوق قرار دهید. از ساخت پوشه‌های بی‌نام یا موازی خودداری فرمایید.

### گام دوم: استفاده از الگو
1. فایل [`templates/DOCUMENT_TEMPLATE.md`](./templates/DOCUMENT_TEMPLATE.md) را در پوشه مقصد با نامی با فرمت کباب‌کیس (`kebab-case.md`) کپی کنید.
2. جدول متادیتا را با دقت پر کنید. فیلدهای **Title (EN)** و **Summary (EN)** به زبان انگلیسی بسیار مهم هستند زیرا مستقیماً در تولید ایندکس مدل‌های زبانی استفاده می‌شوند.

### گام سوم: نگارش متن و ساختار
- **زبان مستندات:** متن بدنه مستندات به زبان **فارسی سلیس و حرفه‌ای فنی** نگارش می‌شود؛ اما اصطلاحات تخصصی کد و متادیتاهای ماشینی در کنار معادل فارسی درج می‌گردد.
- **عناوین و سرفصل‌ها:** از `#` فقط یک‌بار برای عنوان اصلی سند استفاده کنید. بخش‌ها با `##` و زیربخش‌ها با `###` تفکیک شوند.
- **بلوک‌های کد:** همیشه نوع زبان برنامه‌نویسی را بعد از سه بک‌تیک مشخص نمایید (` ```typescript `، ` ```bash `، ` ```json `).
- **دیاگرام‌ها:** برای نمایش جریان کار، از دیاگرام‌های متنی استاندارد **Mermaid** (` ```mermaid `) استفاده کنید.
- **لینک‌های معتبر:** به جای آدرس‌های مطلق محلی سیستم خود، از مسیرهای نسبی مارک‌داون (مانند `[متن](../frontend/README.md)`) استفاده نمایید.

## 🤖 اسکریپت تجمیع مستندات برای هوش مصنوعی (`llms.txt`)

برای آنکه مدل‌های هوش مصنوعی (LLMs) بتوانند به صورت خودکار و ساختاریافته به کلیه مستندات، توکن‌ها و معماری پروژه دسترسی داشته باشند، این مخزن از استاندارد جهانی [llmstxt.org](https://llmstxt.org/) پشتیبانی می‌کند.

### نحوه عملکرد اسکریپت:
اسکریپت [`scripts/generate-llms.py`](./scripts/generate-llms.py) به صورت خودکار:
1. تمام فایل‌های مارک‌داون موجود در مستندات را پیمایش می‌کند.
2. جدول متادیتای هر سند را می‌خواند و مقادیر **Title (EN)**، **Summary (EN)** و **Category** را استخراج می‌کند.
3. فایل ساختاریافته و انگلیسی [`llms.txt`](./llms.txt) را بر اساس دسته‌بندی‌های استاندارد در ریشه مستندات تولید و به‌روزرسانی می‌نماید.

### نحوه اجرای اسکریپت:
پس از ایجاد یا ویرایش هر سند، دستور زیر را در ترمینال اجرا کنید:
```bash
python3 scripts/generate-llms.py
```
خروجی در فایل `docs/llms.txt` بازتولید شده و آماده بهره‌برداری توسط تمامی ایجنت‌های توسعه و مدل‌های پردازش زبان خواهد بود.

## ⚖️ قوانین تغییر معماری (ADR Governance)
- برای هرگونه تغییر در استک، تصمیم فنی کلان یا تغییر در مدل داده، باید یک **رکورد تصمیم معماری (ADR)** در پوشه [`architecture/decisions/`](./architecture/decisions/) مطابق الگوی [`architecture/decisions/_template.md`](./architecture/decisions/_template.md) ثبت شود.
- تغییر کدها بدون ثبت مستندات تاییدشده معماری در این پوشه، در فرآیند Code Review رد خواهد شد.
