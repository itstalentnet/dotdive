# اصول ریسپانسیو — تصمیم‌های درست برای همه‌ی اندازه‌های صفحه
## Responsive Decision Principles — زاویه‌ی سوم: چیدمان الگوریتمی به‌جای طرح‌های جدا برای هر سایز

> **ارتباط با سایر اسناد بنیادین دیزاین سیستم:**  
> - **زاویه اول ([DOC-DS-007](./design-decision-principles.md)):** اصول تصمیم‌گیری برای فاصله‌گذاری، تایپوگرافی، پالت رنگ، موشن و دسترسی‌پذیری.  
> - **زاویه دوم ([DOC-DS-008](./container-relationship-and-inheritance.md)):** معماری وراثت در کانتینرها، رادیوس هم‌مرکز و متغیرهای چگالی والد-فرزند.  
> - **زاویه سوم (این سند — DOC-DS-009):** چیدمان الگوریتمی و ترکیبی، تطبیق مستقل از بافت، رفتار پازلی گریدها، بارگذاری تطبیقی تصاویر و قوانین ناوبری در صفحات متغیر.

> **ریشه‌ی علمی:**  
> این مفهوم دقیقاً همان چیزی است که در صنعت به آن **Algorithmic / Composable Layout Design** می‌گویند — مکتبی که با «Every Layout» (هیدن پیکرینگ و اندی بل) و پیش از آن با مقاله‌ی بنیان‌گذار «Responsive Web Design» اثن مارکوت (۲۰۱۰) رسمیت پیدا کرد.  
> اصل مرکزی‌شان: **«اگر داری با CSS کشتی می‌گیری، یعنی داری تصمیماتی می‌گیری که باید به مرورگر واگذار می‌شد.»**  
> به‌جای طراحی صفحه برای چند سایز مشخص (موبایل/تبلت/دسکتاپ) و کشیدن خط‌کش بین‌شان، کامپوننت‌ها باید **مستقل از بافت (context-independent)** طراحی شوند تا خودشان بر اساس فضای در دسترس تصمیم بگیرند.

## ۱. چرا «چند طرح ثابت» اشتباه است

پژوهش اندی بل روی بیش از ۱۲۰ هزار بازدید واقعی نشان داد **بیش از ۲٬۳۰۰ اندازه‌ی صفحه‌نمایش منحصربه‌فرد** وجود دارد؛ نتیجه‌ای که او از آن گرفت این بود که **«صفحه‌نمایش ایده‌آل وجود ندارد»** و بنابراین هیچ مجموعه‌ی ثابتی از breakpoint نمی‌تواند همه‌ی حالت‌ها را پوشش دهد. اگر طراحی فقط برای سه سایز «موبایل/تبلت/دسکتاپ» تست شود، صدها هزار عرض صفحه‌ی بینابینی (مثل یک تبلت‌شده در حالت split-screen، یک پنجره‌ی مرورگر نیمه‌باز روی دسکتاپ) شکسته باقی می‌مانند.

**نتیجه‌ی عملی:** breakpoint را نباید بر اساس «دستگاه» تعیین کرد، بلکه بر اساس **جایی که چیدمان واقعاً می‌شکند**. و مهم‌تر از آن، در بسیاری از موارد اصلاً نباید breakpoint دستی نوشت — بگذار خودِ الگوریتم چیدمان (Grid/Flexbox) تصمیم بگیرد.

## ۲. گرید پازلی: ستون‌ها بر اساس عرض تصمیم می‌گیرند، نه بر اساس دستور دستی

با CSS Grid می‌توان گفت «هر ستون حداقل این‌قدر عرض داشته باشد» و اجازه داد خود مرورگر تعداد ستون‌ها را برای هر عرض صفحه محاسبه کند — بدون نوشتن حتی یک media query:

```css
.grid {
  display: grid;
  gap: 1rem;
  grid-template-columns: repeat(auto-fit, minmax(min(18rem, 100%), 1fr));
}
```

- `minmax(280px, 1fr)` یعنی: هر آیتم حداقل ۲۸۰px باشد، اما اگر فضای اضافه بود، به‌طور مساوی بین ستون‌های موجود پخش شود.
- `auto-fit` یعنی تعداد ستون‌ها خودکار بر اساس عرض کانتینر (نه کل صفحه) محاسبه می‌شود؛ وقتی عرض کم می‌شود، ستون‌ها به‌طور طبیعی به ردیف بعدی «می‌ریزند» — دقیقاً رفتار پازلی.
- **نکته‌ی مهم فنی:** به‌جای `minmax(280px, 1fr)` خالص، از `minmax(min(280px, 100%), 1fr)` استفاده کنید تا وقتی کانتینر از ۲۸۰px هم باریک‌تر شد (مثلاً موبایل‌های بسیار کوچک)، آیتم مجبور به overflow افقی نشود.

### ۲.۱ چه زمانی این کافی نیست
وقتی محتوا نیاز به یک ترتیب متفاوت (نه فقط تعداد ستون متفاوت) دارد — مثلاً یک تصویر که باید در موبایل بالا و در دسکتاپ کنار متن باشد — گرید خودکار کافی نیست و باید صریحاً چیدمان را در آن نقطه بازآرایی کرد (معمولاً با `grid-template-areas` که در یک breakpoint واقعی، نه فرضی، عوض می‌شود).

### ۲.۲ Container Queries — پازل واقعی، نه فقط بر اساس عرض کل صفحه
یک کامپوننت (مثل کارت) ممکن است در یک صفحه‌ی عریض ولی داخل یک ستون باریک (سایدبار) قرار بگیرد. رفتار ریسپانسیوِ آن کامپوننت باید بر اساس **عرض والد مستقیم خودش** تصمیم بگیرد، نه عرض کل viewport — این دقیقاً کاری‌ست که Container Queries انجام می‌دهد و امروز به‌خوبی در مرورگرهای مدرن پشتیبانی می‌شود:

```css
.card-container {
  container-type: inline-size;
  container-name: card;
}

@container card (min-width: 480px) {
  .card-inner {
    display: flex;
    flex-direction: row;
  }
}
```

## ۳. تصاویر: مقیاس با نسبت، نه با عدد ثابت

### ۳.۱ قانون پایه: هرگز عرض/ارتفاع را px مطلق ندهید
```css
img {
  max-width: 100%;
  height: auto;
}
```
این تضمین می‌کند تصویر هرگز از کانتینرش بزرگ‌تر نشود، اما با `aspect-ratio` می‌توان همزمان جلوی «پرش چیدمان» (layout shift) هنگام لود شدن تصویر را هم گرفت:
```css
img {
  width: 100%;
  aspect-ratio: 16 / 9; /* یا هر نسبتی که تصویر واقعاً دارد */
  object-fit: cover; /* یا contain، بسته به این‌که برش مجاز است یا نه */
}
```

### ۳.۲ حداقل و حداکثر اندازه
تصویر باید با همان نسبت (aspect ratio) با عرض کانتینر اسکیل شود، اما بین یک **حداقل و حداکثر منطقی** محدود بماند تا نه در صفحه‌ی خیلی بزرگ بیش‌ازحد کشیده شود و نه در صفحه‌ی خیلی کوچک غیرقابل‌خواندن شود:
```css
.hero-image {
  width: clamp(240px, 60vw, 960px);
  aspect-ratio: 3 / 2;
}
```

### ۳.۳ فایل‌های متفاوت برای عرض‌های متفاوت (نه فقط اسکیل CSS)
اسکیل‌کردن یک تصویر بزرگ با CSS مشکل عملکرد ایجاد می‌کند (کاربر موبایل فایل حجیم دسکتاپ را دانلود می‌کند). راه‌حل درست `srcset` + `sizes` است تا مرورگر خودش بهترین نسخه را بر اساس عرض واقعی رندرشده انتخاب کند:
```html
<img
  src="image-800.jpg"
  srcset="image-400.jpg 400w, image-800.jpg 800w, image-1200.jpg 1200w"
  sizes="(max-width: 768px) 100vw, 50vw"
  alt="..." />
```
وقتی تصویر باید در نسبت‌های کاملاً متفاوت (نه فقط سایز، بلکه crop متفاوت — مثلاً عکس افقی در دسکتاپ و عمودی در موبایل) نمایش داده شود، به‌جای `srcset`، از `<picture>` با چند `<source media="...">` استفاده کنید (Art Direction).

## ۴. چه زمانی به کاروسل/اسلایدر تبدیل شود؟ (با احتیاط جدی)

### ۴.۱ شواهد علیه استفاده‌ی پیش‌فرض از کاروسل
شواهد پژوهشی علیه کاروسل‌های خودکار (auto-rotating) بسیار قوی است:
- تحقیقات **Nielsen Norman Group** نشان داده کاربران معمولاً کاروسل‌ها را به‌خاطر «کوری بنری» (banner blindness) نادیده می‌گیرند.
- مطالعه‌ی معروف **دانشگاه نوتردام (Notre Dame)** نشان داد فقط حدود **۱٪** از بازدیدکنندگان روی اسلایدها کلیک می‌کنند و **۸۴٪** از آن کلیک‌ها فقط روی اسلاید اول است.
- چرخش خودکار مانع خواندن متن توسط کاربران با سرعت‌های مطالعه متفاوت می‌شود.

> 🚫 **قانون عملی:** به‌طور پیش‌فرض کاروسل خودکار نسازید؛ اگر واقعاً چند پیام باید نمایش داده شود، ناوبری دستی (بدون autoplay) یا صرفاً یک گرید/لیست ساده بسیار کارآمدتر است.

### ۴.۲ موردی که کاروسل/اسکرول افقی واقعاً توجیه دارد
تبدیل گرید به کاروسل بیشتر درباره‌ی **گرید محصولات/کارت‌ها در فضای محدود موبایل** است:

| شرایط | تصمیم |
|---|---|
| آیتم‌ها از یک **مجموعه‌ی هم‌رتبه و قابل‌مرور** هستند (محصولات مشابه، دسته‌بندی‌ها) و کاربر قرار نیست همه را ببیند، فقط چند نمونه کافی‌ست | اسکرول افقی/کاروسل با ناوبری **دستی**، بدون autoplay کاملاً قابل‌قبول است |
| محتوا **باید کامل دیده شود** (فهرست کامل نتایج، مقایسه‌ی همه‌ی گزینه‌ها) | هرگز کاروسل نشود — گرید عمودی با اسکرول طبیعی صفحه |
| فقط ۲–۳ آیتم دارید که در عرض موبایل جا نمی‌شوند | اول اسکیل‌کردن گرید (کاهش تعداد ستون به ۱) را پیاده کنید؛ کاروسل فقط وقتی توجیه دارد که تعداد آیتم واقعاً برای مرور افقی مناسب باشد (۴ به بالا) |
| کاروسل تنها راه دسترسی به یک CTA یا اطلاعات حیاتی است | هرگز — اطلاعات حیاتی هرگز نباید پشت یک اسلاید پنهان شود |

> ⚠️ طبق تحقیقات **Baymard Institute** فقط حدود **۲۳٪** از بازدیدکنندگان موبایل محتوایی را که نیاز به اسکرول افقی دارد کشف می‌کنند. بنابراین **کاروسل همیشه آخرین انتخاب است، نه اولین گزینه**.

## ۵. تب‌بار → دراپ‌دون/Overflow: الگوی Priority+

### ۵.۱ ایده و منطق پیاده‌سازی
این الگو (که برد فراست رسماً مستند کرده و امروز با Container Queries به‌شکل بسیار تمیزتری قابل‌پیاده‌سازی است) پهنای در دسترس نوار تب/ناوبری را می‌سنجد: تا وقتی همه‌ی آیتم‌ها جا می‌شوند به همان شکل افقی نمایش داده می‌شوند؛ وقتی جا کم آمد، آیتم‌های کم‌اهمیت‌تر (از انتهای ترتیب خواندن) به یک دکمه‌ی **«بیشتر / More»** منتقل می‌شوند که با کلیک یک دراپ‌داون باز می‌کند.

```css
.tabs {
  container-type: inline-size;
}

@container (max-width: 350px) {
  .tabs-item:nth-child(n + 4):not(:last-child) {
    display: none;
  }
  .tabs-item:last-child {
    display: block; /* دکمه‌ی "بیشتر" */
  }
}
```

### ۵.۲ چرا این الگو بهتر از Hamburger کامل است
تحقیقات نشان داده الگوی Priority+ نسبت به مخفی‌کردن کامل ناوبری پشت یک آیکون همبرگری، **کشف‌پذیری بهتری** دارد — چون همیشه چند مقصد پراستفاده مستقیماً در دید کاربر باقی می‌ماند و تنها موارد فرعی مخفی می‌شوند.

### ۵.۳ قانون تصمیم کلی برای ناوبری در فضای محدود
- **تعداد آیتم کم (۳–۵) و فضا کافی:** همه به‌صورت افقی/تب استاندارد.
- **فضا محدود می‌شود:** آیتم‌های کم‌اهمیت‌تر به دراپ‌داون «بیشتر» منتقل شوند (Priority+)، نه به یک منوی کاملاً پنهان.
- **در موبایل:** در نوار ابزار یا هدر، تبدیل گزینه‌ها به منوی Action Sheet / Bottom Sheet در صورت افزایش گزینه‌ها به بیش از ۵ مورد پیشنهاد می‌شود.

## ۶. عدم استفاده از ابعاد ثابت — همه‌چیز باید «نسبت» داشته باشد، نه پیکسل مطلق

این اصل مرکزی کل معماری چیدمان است: عناصر باید بر اساس روابط ریاضی منعطف باشند، نه مقادیر مطلق صلب.

### ۶.۱ واحدهای نسبی به‌جای px مطلق
| به‌جای | استفاده کنید از |
|---|---|
| عرض ثابت px برای کانتینرهای محتوایی | `%`، `fr` (در گرید)، یا `max-width` + `width: 100%` |
| فونت‌سایز ثابت px که در breakpointها جهش می‌کند | `clamp(min, preferred, max)` برای مقیاس نرم بین دو مقدار |
| ارتفاع ثابت px برای کارت‌های حاوی تصویر | `aspect-ratio` به‌جای height مطلق |
| Padding/Margin ثابت که در موبایل هم عیناً حفظ می‌شود | مقیاس کوچک‌تر و متناسب طبق [DOC-DS-007](./design-decision-principles.md) — حفظ نسبت‌ها، نه مقدار مطلق |

### ۶.۲ چرا این موضوع حیاتی است
وقتی یک باکس عرض ثابت ۴۰۰px دارد، در صفحه‌ی ۳۲۰px (کوچک‌ترین موبایل‌های رایج) overflow افقی ایجاد می‌کند — این یکی از رایج‌ترین دلایل شکستن UI در صفحات کوچک است. با تعریف رابطه به‌جای عدد مطلق (`width: min(400px, 100%)`)، همان کامپوننت خود را با هر عرضی که در اختیار دارد وفق می‌دهد.

### ۶.۳ Mobile-first به‌عنوان یک روش مهندسی
استایل پایه برای کوچک‌ترین حالت (بدون هیچ media query) نوشته می‌شود؛ سپس با `min-width` پیچیدگی افزوده می‌شود، نه برعکس. این روش کارایی مرورگر را افزایش داده و طراح و توسعه‌دهنده را ملزم به اولویت‌بندی محتوای واقعاً ضروری پیش از پرداختن به جزئیات ثانویه می‌کند.

## ۷. دکمه‌ی بازگشت — جایگاه، رفتار و تطبیق با جهت متن

### ۷.۱ محل استاندارد و Mirroring دوزبانه
در هر دو سیستم‌عامل iOS و Android، دکمه‌ی بازگشت به‌صورت استاندارد در **گوشه‌ی بالا-سمتِ شروعِ خواندن** (top-leading) قرار می‌گیرد:
- در رابط‌های چپ‌به‌راست (LTR): بالا-چپ با پیکان رو به چپ.
- **در رابط‌های راست‌به‌چپ (RTL نظیر فارسی):** دقیقاً آینه‌ای شده و در **بالا-راست** با جهت پیکان به سمت راست قرار می‌گیرد.
- عدم رعایت این آینه‌سازی (mirroring)، رابط کاربری را برای کاربران فارسی‌زبان کاملاً معکوس و غیرطبیعی جلوه می‌دهد.

### ۷.۲ تفاوت Back و Up
- **Up (ناوبری سلسله‌مراتبی):** بر اساس **سلسله‌مراتب ساختاری اپ** حرکت می‌کند (از صفحه‌ی جزئیات یک آیتم به لیستی که آیتم از آن باز شده) و همواره کاربر را داخل اکوسیستم اپ نگه می‌دارد.
- **Back (ناوبری زمانی):** بر اساس **تاریخچه‌ی زمانی واقعی مرور کاربر** حرکت می‌کند و می‌تواند کاربر را حتی به اپ قبلی یا موتور جستجو بازگرداند.
- هنگامی که کاربر از طریق دیپ‌لینک یا نوتیفیکیشن وارد عمق برنامه می‌شود، این دو رفتار متفاوت عمل می‌کنند. کامپوننت باید صریحاً برای رفتار سلسله‌مراتبی (Up) برنامه‌ریزی شود.

### ۷.۳ قانون دید کافی (Visibility) برای دکمه‌ی بازگشت
- هرگز دکمه‌ی بازگشت را زیر خط تا (below the fold) یا پشت اسکرول قرار ندهید — همیشه باید بدون اسکرول در دید اول باشد (`position: sticky` یا داخل هدر ثابت).
- ناحیه‌ی لمسی (Touch Target) دکمه‌ی بازگشت باید حداقل **۴۴×۴۴px** باشد، حتی اگر آیکون بصری آن ۲۰px باشد.
- در صفحه‌ی ریشه‌ی ناوبری (Home / Root Workspace)، دکمه‌ی بازگشت نباید نمایش داده شود.

## ۸. چک‌لیست خودارزیابی ریسپانسیو (Responsive Audit Checklist)

- [ ] آیا حداقل یک عرض تست‌شده کوچک‌تر از ۳۲۰px بدون overflow افقی کار می‌کند؟
- [ ] آیا تعداد ستون‌های گرید با `auto-fit`/`minmax` خودکار تعیین می‌شود، نه با media queryهای دستی و حدسی؟
- [ ] آیا هر عرض/ارتفاع ثابت px با یک نسبت یا `clamp()`/`%` جایگزین شده است؟
- [ ] آیا تصاویر با `aspect-ratio` + `object-fit` بدون layout shift اسکیل می‌شوند و با `srcset` بارگذاری بهینه دارند؟
- [ ] اگر از کاروسل استفاده شده، آیا این تصمیم آخرین گزینه بوده (نه اولین)، و آیا autoplay غیرفعال است؟
- [ ] آیا هیچ اطلاعات یا CTA حیاتی پشت یک اسلاید یا اسکرول افقی پنهان نشده است؟
- [ ] آیا ناوبری در فضای محدود به الگوی Priority+ (دراپ‌داون «بیشتر») تبدیل می‌شود، نه پنهان‌سازی کامل؟
- [ ] آیا دکمه‌ی بازگشت در گوشه‌ی درست (با توجه به RTL/LTR) و همیشه در دید بدون اسکرول قرار دارد؟
- [ ] آیا صفحه‌ی ریشه فاقد دکمه‌ی بازگشت نامربوط است؟
- [ ] آیا کامپوننت‌های قابل‌استفاده‌ی مجدد (کارت، ویجت) رفتار ریسپانسیوشان را بر اساس Container Query تعیین می‌کنند، نه فقط عرض کل صفحه؟
