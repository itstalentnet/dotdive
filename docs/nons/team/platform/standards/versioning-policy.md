# سیاست نسخه‌بندی
**Versioning Policy**

نسخه 1.0 | الزامی برای همه سرویس‌ها، پکیج‌ها و انتشارات

---

## 1. استاندارد

همه سرویس‌ها و پکیج‌ها از **Semantic Versioning 2.0.0** پیروی می‌کنند:

```
v{MAJOR}.{MINOR}.{PATCH}
  ^     ^     ^
  |     |     |
  |     |     └─── PATCH: تغییرات برگشت‌پذیر (رفع باگ، بهبود)
  |     └───────── MINOR: افزودن قابلیت جدید (برگشت‌پذیر)
  └─────────────── MAJOR: تغییرات ناسازگار (شکستن API)
```

**فرمت کامل:** `v{MAJOR}.{MINOR}.{PATCH}` — مثال: `v1.4.2`

---

## 2. قوانین افزایش نسخه

### MAJOR — تغییر ناسازگار (Breaking Change)
- حذف یا تغییر یک endpoint
- تغییر امضای یک رویداد (payload)
- حذف یک فیلد از پاسخ API
- تغییر نوع دیتابیس یا ساختار جدول
- ارتقاء وابستگی اصلی که MAJOR خود را افزایش داده

### MINOR — افزودن قابلیت جدید
- اضافه کردن endpoint جدید
- اضافه کردن فیلد جدید به پاسخ (اختیاری)
- اضافه کردن رویداد جدید
- اضافه کردن قابلیت جدید بدون شکستن قبلی‌ها

### PATCH — رفع باگ / بهبود
- رفع باگ بدون تغییر API
- بهبود عملکرد
- بروزرسانی وابستگی‌های فرعی
- رفع اشکالات امنیتی جزئی

---

## 3. پیش‌انتشار (Pre-release)

برای نسخه‌های آزمایشی از برچسب‌های زیر استفاده کنید:

| برچسب | معنی | مثال |
|---|---|---|
| `-alpha.{n}` | توسعه داخلی، ناپایدار | `1.0.0-alpha.1` |
| `-beta.{n}` | تست محدود، احتمال تغییر | `1.0.0-beta.2` |
| `-rc.{n}` | نامزد انتشار، پایدار اما در انتظار تأیید | `1.0.0-rc.3` |

```bash
nons/auth:v1.0.0-alpha.1
nons/auth:v1.0.0-beta.1
nons/auth:v1.0.0-rc.1
nons/auth:v1.0.0
```

---

## 4. نسخه‌بندی مستقل

| موجودیت | نسخه مستقل | توضیح |
|---|---|---|
| سرویس (Service) | بله | هر سرویس نسخه مستقل خود را دارد |
| پکیج (Package) | بله | هر پکیج نسخه مستقل خود را دارد |
| پروژه (Monorepo) | خیر | نسخه در سطح سرویس/پکیج است |

> یک سرویس ممکن است `v2.0.0` باشد در حالی که سرویس دیگر در `v1.3.5` است. این کاملاً طبیعی است.

---

## 5. انتشار (Release)

### چرخه انتشار

```
توسعه → تست → پیش‌انتشار → انتشار نهایی
```

### قوانین
- هر انتشار باید یک **Git Tag** داشته باشد: `{service}/v{version}` 
  - مثال: `order/v1.2.0`, `nons-api/contracts/v0.4.1`
  - برای Proto: `nons-api/contracts/v{major}.{minor}.{patch}` — هماهنگ با SemVer سرویس‌ها
- هر انتشار باید یک **GitHub Release** داشته باشد
- هر انتشار باید CHANGELOG به‌روز شده داشته باشد
- انتشار بدون نسخه معتبر ممنوع است
- پس از انتشار، نسخه قابل تغییر نیست — اگر اشتباه شد، نسخه جدید منتشر کنید
- **تغییر Proto:** افزودن فیلد جدید ← MINOR | حذف یا تغییر فیلد ← MAJOR (توسط Buf تشخیص داده می‌شود)

### برچسب‌گذاری (Tagging)

```bash
git tag auth/v1.0.0
git tag order/v2.0.0-alpha.1
git tag nons-api/contracts/v0.4.1
git push origin --tags
```

## 6. وابستگی نسخه‌ها (Version Compatibility)

| سناریو | قانون |
|---|---|
| سرویس A به سرویس B وابسته است | سرویس A باید محدوده MAJOR سرویس B را مشخص کند |
| پکیج به پکیج دیگر وابسته است | محدوده دقیق نسخه در `package.json` / `go.mod` |
| نسخه سرویس در کانفیگ | نسخه سرویس باید در متغیر محیط `SERVICE_VERSION` باشد |

```json
{
  "dependencies": {
    "@nons/contracts": "^1.0.0",
    "@nons/events": "^1.0.0"
  }
}
```

**نکته:** نسخه‌بندی Bindingهای تولیدشده از Proto با نسخه Proto هماهنگ است. Bindingها در CI تولید می‌شوند — ویرایش دستی نسخه Bindingها ممنوع. تایپ‌های فرانت‌اند توسط `nons generate` در `.nons/generated/types/` تولید می‌شوند.

### Service Manifest و API — ماتریس سازگاری (ADR-Platform-004)

با تصویب [ADR-Platform-004](../ADR/ADR-Platform-004)، **Service Manifest** منبع حقیقت برای تولید مصنوعات کلاینت است. APIها از طریق Service Manifest با پروژه‌های کلاینت هماهنگ می‌شوند. جفت‌شدگی خطی ممنوع است. هر Manifest به صورت صریح مشخص می‌کند با کدام نسخه‌های فعال API سازگار است:

| Manifest Version | API Version |
| :--- | :--- |
| 1.x | v1 |
| 2.x | v1, v2 |
| 3.x | v2 |

بررسی سازگاری توسط `nons validate` انجام می‌شود.

هر ایمیج داکر باید با نسخه دقیق تگ شود:

```
nons/order:v1.2.0
nons/order:v1.2.0-alpha.1
```

## 8. مستندات نسخه‌بندی

- هر سرویس باید نسخه فعلی خود را در `CHANGELOG.md` اعلام کند
- API همیشه نسخه خود را در مسیر دارد: `/v1/`, `/v2/`
- تغییرات MAJOR نیاز به مستندات مهاجرت (Migration Guide) دارند

## خلاصه

| نوع تغییر | افزایش | مثال |
|---|---|---|
| رفع باگ برگشت‌پذیر | PATCH | `v1.0.0` ← `v1.0.1` |
| قابلیت جدید برگشت‌پذیر | MINOR | `v1.0.0` ← `v1.1.0` |
| تغییر ناسازگار | MAJOR | `v1.0.0` ← `v2.0.0` |
| پیش‌انتشار | + برچسب | `v2.0.0-alpha.1` |
