# مسیر توسعه

**Development Roadmap**

این سند نقشه راه رسمی توسعه پروژه است و جایگزین تمام فازبندی‌های قبلی (از جمله فازبندی داخل `docs/blueprint.md`) می‌شود.  
نکته کلیدی: **توسعه به صورت افزایشی و سرویس‌به‌سرویس** انجام می‌شود.  
ما ابتدا برای همه سرویس‌ها فقط یک README پیشنهادی و پایه می‌نویسیم.  
سپس قدم به قدم، هر سرویس را کامل می‌کنیم (بلوپرینت ← دمو ← مستندات تکمیلی ← خروجی قابل تحویل).  
هیچ‌کس برای ۱۸ سرویس با هم دمو نمی‌سازد. تمرکز روی یک سرویس در هر مرحله است.

---

## اصول کلیدی توسعه

1. **اول مستندات پیشنهادی، نه دمو**  
   در فاز آماده‌سازی، فقط یک README ساده برای هر سرویس نوشته می‌شود شامل:
   - معماری پیشنهادی پایه
   - مسئولیت و وظایف آن سرویس
   - وابستگی‌ها
   - نکته: «این مستند پیشنهادی است و در حین توسعه سرویس‌های قبلی ممکن است تغییر کند»

2. **پایه‌گذاری قبل از سرویس‌ها**  
   ابتدا لایه قراردادها (`nons-api/contracts/` Proto)، پکیج‌های مشترک (`nons-api/core`, `nons-api/packages/types`, `nons-api/packages/contracts`)، زیرساخت محلی و CI/CD ساده راه‌اندازی می‌شود.

3. **توسعه سرویس‌به‌سرویس**  
   بعد از پایه‌گذاری، یک سرویس را انتخاب می‌کنیم و تا انتها کامل می‌کنیم:
   - بازبینی و تکمیل بلوپرینت آن سرویس
   - ساخت دمو (نمایشی از کارکرد اصلی)
   - تکمیل مستندات آن سرویس (API، رویدادها، خطاها)
   - تست و تحویل خروجی
   - سپس رفتن به سرویس بعدی

4. **مستندات زنده هستند**  
   مستندات معماری اولیه (فاز 1-) «پیشنهادی» هستند و ممکن است بعد از توسعه سرویس‌های قبلی تغییر کنند.  
   مستندات نهایی و قابل اعتماد بعد از اتمام هر سرویس به‌روز می‌شوند.

5. **قرارداد ثبت وقایع (Logging Contract) مستقل از پیاده‌سازی**  
   سرویس‌ها در انتخاب کتابخانه و پیاده‌سازی ثبت وقایع (Logger Implementation) آزاد هستند، اما تمام وقایع ثبت‌شده باید با **قرارداد ثبت وقایع پلتفرم** مطابقت داشته باشند.  
   - **قرارداد (Logging Standard):** فرمت JSON، فیلدهای اجباری (`correlationId`, `service`, `timestamp`, `level`, `message`)، سطوح `DEBUG/INFO/WARN/ERROR`
   - **پیاده‌سازی (Logger Implementation):** آزاد — پیشنهاد: Go ← `slog`، Node.js ← `pino`، Python ← `structlog`
   - این تفکیک در `nons-api/packages/logging` به صورت قرارداد (types, interfaces, validators) تعریف می‌شود، نه پیاده‌سازی نهایی.

## فاز ۰ — پایه‌گذاری `(Foundation)`

> هدف: پروژه آماده کدنویسی بشه — هنوز هیچ سرویس تخصصی نوشته نشده

- [x] **M0.2:** پیاده‌سازی ساختار قراردادها و پکیج‌های مشترک:
  - [x] اسکلت‌بندی و راه‌اندازی اولیه‌ی پکیج‌های TypeScript در `nons-api/packages/*` به صورت ساختار خام و کامپایل‌شونده (`types`, `contracts`, `events`, `logging`, `client`)
  - [x] تعریف ساختار قراردادها با فایل‌های `.proto` در مسیر `nons-api/contracts/` (شامل `envelope.proto`، `registry.proto`، `errors.proto` و `permissions.proto`) به عنوان منبع واحد حقیقت (Source of Truth) پلتفرم
  - [x] پیکربندی و راه‌اندازی ابزار **Buf** (`buf.yaml` و `buf.gen.yaml`) جهت تولید خودکار (Code Generation) تایپ‌های TypeScript و سورس کدهای Go از فایل‌های Proto
  - [x] جایگزینی پکیج‌های موقت TypeScript با خروجی بیلد خودکار قراردادها (شامل `nons-api/packages/types`، `nons-api/packages/contracts` و `nons-api/packages/events`)
  - [x] نهایی‌سازی ساختار `nons-api/packages/logging` جهت مدیریت قرارداد لاگینگ پلتفرم (خارج از ساختار Proto)
- [x] **M0.3:** پیاده‌سازی سرویس هسته Go (موتور رویداد، ثبت خدمات، لاگ حسابرسی، اعتبارسنجی فنی رویدادها)
  - *نکته معماری*: سرویس Core کاملاً فاقد دانش نسبت به دامنه‌های کسب‌وکار (Domain Agnostic) است. بر این اساس، **ماشین حالت سفارش** در Core پیاده‌سازی نخواهد شد و پیاده‌سازی آن در سرویس سفارش (`order-service` - Milestone M1.4) انجام می‌گردد.
  - سرویس Core با استفاده از Go Bindings تولید شده از روی قراردادهای `.proto` پیاده‌سازی می‌شود.
- [x] **M0.4:** راه‌اندازی زیرساخت محلی با K3d و Helm (PostgreSQL، MongoDB، Redis، NATS، API Gateway، Go core)
- [x] **M0.5:** راه‌اندازی CI/CD پایه (GitHub Actions: lint، build، test ساده برای پکیج‌های مشترک + Code Generation با Buf)

### ✅ خروجی فاز ۰

مونوریپو آماده، لایه Proto تعریف شده، پکیج‌های مشترک بروزرسانی شده، هسته Go قابل اجرا، زیرساخت محلی K3d و Helm راه‌اندازی شده.  
هیچ سرویس تخصصی (auth, marketplace, ...) هنوز نوشته نشده.

#### **M1.1** - `auth-service` (کامل) — مبتنی بر **Ory Kratos** (سرویس آماده خارجی)
- [] بازبینی README پیشنهادی فاز ۱-
- [] آشنایی با مستندات و APIهای Ory Kratos
- [] پیکربندی Kratos برای نیازهای پلتفرم (فعال‌سازی `code` و `oidc`، غیرفعال‌سازی `password`)
- [] پیکربندی Google OIDC provider در Kratos
- [] پیکربندی SMTP برای ارسال Magic Code
- [] ساخت دمو (ورود با Magic Code، ورود با Google، Auto Sign-Up، تشخیص کاربر جدید)
- [] تکمیل مستندات (API، رویدادها، خطاها، معماری نهایی)
- [] تست و خروجی تأیید شده

> این سرویس از صفر توسعه داده نمی‌شود — از قابلیت‌های آماده Ory Kratos استفاده می‌کند.
>
> **روش‌های احراز هویت:**
> - **Primary:** Magic Code (ورود با ایمیل + کد یکبار مصرف)
> - **Secondary:** Google Login (ورود با حساب Google + تطبیق خودکار ایمیل)
> - روش‌های `password` و `discord` از معماری فعال حذف شده‌اند.

#### **M1.1.5** - `token-service` (کامل) — **NEW**
- بازبینی Blueprint (`services/token-service/blueprint.md`)

- افشای JWKS endpoint (`/.well-known/jwks.json`) و OIDC discovery
- صدور access/refresh/id token + فعال‌سازی Refresh Token Rotation
- پیاده‌سازی middleware اعتبارسنجی stateless JWT در یک میکروسرویس pilot
- انتشار رویدادها: `nons.token.issued`, `nons.token.revoked`
- تکمیل مستندات (API، Events، Architecture)
- تست و خروجی

> token-service از قابلیت‌های آماده Ory Hydra استفاده می‌کند. صدور و اعتبارسنجی توکن از auth-service جدا شده است.

## فاز ۰.۵ — زیرساخت تحویل کانتینر (Container Delivery Infrastructure)

#### **M0.5.1** — Container Registry Integration
- **Purpose:** ایجاد مخزن رسمی کانتینر برای پلتفرم NONS در ghcr.io
- **Dependencies:** حساب سازمانی GitHub، دسترسی Devops به تنظیمات Packages
- **Expected phase:** فاز ۰.۵
- **Architectural impact:** تعیین منبع حقیقت تصاویر — تمام CI/CD workflows به این registry متصل می‌شوند

#### **M0.5.2** — Automated Image Builds
- **Purpose:** ساخت خودکار تصویر کانتینر برای هر commit به main + هر PR
- **Dependencies:** Container Registry Integration (M0.5.1)
- **Expected phase:** فاز ۰.۵
- **Architectural impact:** حذف Build دستی — هر commit دارای SHA Tag در registry است

#### **M0.5.3** — CI/CD Pipeline Implementation
- **Purpose:** پیاده‌سازی pipeline کامل: PR validation → Build → Push → Staging Deploy → E2E → Production Gate
- **Dependencies:** Automated Image Builds (M0.5.2), Helm Charts موجود
- **Expected phase:** فاز ۰.۵
- **Architectural impact:** استقرار خودکار Staging، Production با گیت دستی

#### **M0.5.4** — Deployment Automation
- **Purpose:** خودکارسازی Helm upgrade به Staging پس از build موفق
- **Dependencies:** CI/CD Pipeline (M0.5.3)
- **Expected phase:** فاز ۰.۵
- **Architectural impact:** حذف دستورات دستی `helm upgrade` برای Staging

#### **M0.5.5** — GitOps Evaluation
- **Purpose:** بررسی ArgoCD/Flux برای استقرار declarative
- **Dependencies:** CI/CD Pipeline (M0.5.3), maturity فاز ۵
- **Expected phase:** فاز ۵
- **Architectural impact:** تغییر مدل استقرار از imperative (helm upgrade) به declarative (GitRepo sync)

#### **M0.5.6** — Supply Chain Security Enhancements
- **Purpose:** امضای تصاویر (Cosign)، اسکن vulnerability (Trivy)، تولید SBOM (Syft)
- **Dependencies:** CI/CD Pipeline (M0.5.3)
- **Expected phase:** فاز ۵
- **Architectural impact:** اعمال policy enforcement برای تصاویر اسکن‌نشده

#### **M0.5.7** — Multi-Architecture Image Support
- **Purpose:** پشتیبانی از linux/amd64 + linux/arm64
- **Dependencies:** BuildKit, CI/CD Pipeline
- **Expected phase:** فاز ۵
- **Architectural impact:** افزایش زمان build, نیاز به QEMU در CI

#### **M0.5.8** — Progressive Delivery Capabilities
- **Purpose:** Canary deployment, feature flags, traffic splitting
- **Dependencies:** GitOps (M0.5.5), Service Mesh
- **Expected phase:** پس از فاز ۵
- **Architectural impact:** نیاز به Service Mesh (Istio/Linkerd) + Flagger/Argo Rollouts

## موارد خارج از MVP منتقل‌شده به نقشه راه (Roadmap Relocation - D4)

به منظور بهینه‌سازی دامنه MVP و تمرکز بر راه‌اندازی فرآیندهای حیاتی کسب‌وکار، موارد زیر از معماری فعال MVP خارج شده و به نقشه راه (Roadmap) منتقل شده‌اند:

### ۱. چارت مستقر در کوبرنتیز مونگودی‌بی (MongoDB Helm Chart)
- **دلیل عدم نیاز در MVP:** در فاز MVP، چت گفتگوی کاربران حجم بسیار کمی داشته و نیازی به یک کلاستر توزیع‌شده با قابلیت دسترسی بالا برای MongoDB نیست. اجرای تک‌نمونه‌ای پایگاه‌داده موقت محلی برای اعتبارسنجی اولیه گفتگوها کافی است.
- **زمان تقریبی ورود:** فاز ۲ (اعتماد و داوری)، همزمان با توسعه کامل `storage-service` (Milestone M2.6).
- **وابستگی‌ها:** پیکربندی صحیح Persistent Volumes (PV/PVC) و StorageClassها روی کلاستر هدف.
- **اثر بر معماری:** انتقال Chat Service از ذخیره‌ساز محلی به StatefulSetهای مقیاس‌پذیر MongoDB در کوبرنتیز به همراه تضمین ماندگاری داده‌ها برای داوری اختلافات.

### ۲. چارت مستقر در کوبرنتیز تایگربیتل (TigerBeetle Helm Chart)
- **دلیل عدم نیاز در MVP:** دفترکل تراکنش‌های مالی در فاز MVP می‌تواند به صورت یک پایگاه‌داده تک‌نسخه‌ای محلی موقت اجرا شود. عدم استفاده از چارت توزیع‌شده تایگربیتل در ابتدا، پیچیدگی استقرار اولیه را کاهش می‌دهد.
- **زمان تقریبی ورود:** فاز ۵ (مقیاس و بهینه‌سازی)، Milestone M5.4.
- **وابستگی‌ها:** پایداری ارکستراسیون حافظه ماندگار Stateful و مکانیزم‌های بازیابی شبکه در کلاستر.
- **اثر بر معماری:** تغییر مدل استقرار لجر مالی از تک‌کانتینر توسعه محلی به کلاستر توزیع‌شده و خطاتحمل‌پذیر (بر پایه Raft) در کوبرنتیز پروداکشن.

### ۳. پشته مانیتورینگ (Monitoring Stack — Prometheus, Grafana, Jaeger)
- **دلیل عدم نیاز در MVP:** پایش پیشرفته سناریوهای توزیع‌شده و رهگیری درخواست‌ها برای تایید منطق تجاری اولیه ضروری نیست. عیب‌یابی اولیه از طریق بررسی لاگ پادها (`kubectl logs`) کفایت می‌کند.
- **زمان تقریبی ورود:** فاز ۵ (مقیاس و بهینه‌سازی)، Milestone M5.2.
- **وابستگی‌ها:** پیاده‌سازی کامل ابزاردقیق OpenTelemetry روی تمامی میکروسرویس‌ها و پایداری لایه رویداد.
- **اثر بر معماری:** معرفی یک Namespace اختصاصی برای ابزارهای مانیتورینگ، اجرای DaemonSetها برای جمع‌آوری متریک‌ها و لاگ‌ها، و تعریف Sidecarهای مانیتورینگ در کنار پادها.

### ۴. اعتبارسنجی بازیابی پس از بحران (Disaster Recovery Validation)
- **دلیل عدم نیاز در MVP:** هدف اصلی MVP، صحت عملکرد فرآیند خرید و فروش است. فرآیندهای تست خرابی کامل کلاستر و بازیابی چندمنطقه‌ای به فازهای بلوغ عملیاتی موکول می‌شود.
- **زمان تقریبی ورود:** فاز ۵ (مقیاس و بهینه‌سازی)، Milestone M5.4 (Recovery).
- **وابستگی‌ها:** سیستم‌های ذخیره‌سازی ابری ماندگار، اسنپ‌شات‌های خودکار دیتابیس‌ها و سیاست‌های توزیع DNS.
- **اثر بر معماری:** پیاده‌سازی بک‌آپ‌های خودکار و انتقال آن‌ها به ذخیره‌ساز خارجی S3 و ایجاد سناریوهای Failover خودکار برای ترافیک درگاه.

### ۵. توسعه ذخیره‌سازی ماندگار (Persistent Storage Expansion)
- **دلیل عدم نیاز در MVP:** برای توسعه محلی و سناریوهای تست اولیه، استفاده از hostPath یا حجم‌های پیش‌فرض محلی K3d کافی است و نیازی به راه‌اندازی و توسعه درایورهای ذخیره‌سازی ابری پیچیده نیست.
- **زمان تقریبی ورود:** فاز ۵ (مقیاس و بهینه‌سازی)، Milestone M5.7.
- **وابستگی‌ها:** ارائه‌دهندگان ذخیره‌سازی کلاستر هدف (مانند Rook-Ceph، AWS EBS یا ارتقای local-path-provisioner).
- **اثر بر معماری:** افزودن درایورهای CSI پیشرفته، اعمال سیاست‌های افزایش حجم پویای دیسک پادها و تفکیک دیسک‌های با کارایی بالا برای دیتابیس‌ها.
