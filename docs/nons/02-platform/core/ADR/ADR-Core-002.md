# ایجاد Core به عنوان Platform Control Plane

**Core as Platform Control Plane**

> **ADR-Core-002**

---

## وضعیت

**Status**

✅ **تایید شده (APPROVED)**

## تاریخ

**Date**

2026-06-11

## زمینه

**Context**

پروژه NONS بر پایه معماری رویدادمحور و مجموعه‌ای از سرویس‌های مستقل طراحی شده. با افزایش تعداد سرویس‌ها، نیازمندی‌هایی به وجود میاد که متعلق به هیچ دامنه کسب‌وکار (بیزنس) خاصی نیستن، بلکه در سطح کل پلتفرم مطرح هستن؛ مواردی مثل:

- ثبت و رهگیری رویدادها
- اعتبارسنجی فنی رویدادها
- نظارت بر سلامت سرویس‌ها
- مدیریت وضعیت سرویس‌ها
- اعمال استانداردهای فنی مشترک

قرار دادن این مسئولیت‌ها داخل سرویس‌های دامنه‌ای (مثل سفارش یا پرداخت) باعث تکرار منطق، افزایش وابستگی (Coupling) و عدم هماهنگی در سطح کل پلتفرم می‌شه. پس وجود یه لایه مستقل واسه مدیریت دغدغه‌های پلتفرمی کاملاً ضروری هستش.

---

## تصمیم

**Decision**

یه سرویس مستقل به اسم **Core** به عنوان Platform Control Plane رسمی پروژه NONS ایجاد می‌شه.
Core یه سرویس زیرساختیه و بخشی از هیچ کدوم از دامنه‌های کسب‌وکاری نیست.

وظیفه Core مدیریت کارهای فنی مشترک در سطح پلتفرم هست و سرویس‌های دیگه بدون وابستگی مستقیم به اون و صرفاً از طریق Event Bus (NATS) باهاش تعامل دارن.

پیاده‌سازی Core بر اساس ADR-Platform-001 (لایه قراردادها) با زبان Go انجام می‌شه و از بایندینگ‌های Go تولیدشده در مسیر `nons-api/contracts/` برای اعتبارسنجی Envelope و Registry استفاده می‌کنه.

> [!IMPORTANT]
> **Core یه سرویسه، نه یه فریمورک یا کتابخانه مشترک. بقیه سرویس‌ها نباید هیچ وقت کدهای Core رو ایمپورت کنن.**

---

## محدوده مسئولیت

**Scope of Responsibility**

مسئولیت Core فقط به این موارد محدوده:

- Audit Logging
- Technical Event Validation
- Service Registry
- Health Monitoring
- Platform Governance

این وظایف فقط در سطح فنی و زیرساختی تعریف می‌شن و هیچ منطق کسب‌وکاری (بیزنس لوگات) ندارن.

---

## محدودیت‌ها

**Constraints**

Core نباید هیچ مدل دامنه‌ای یا دانش کسب‌وکاری داشته باشه.

نمونه‌هایی از کارهای ممنوعه توی Core:

- احراز هویت و مجوزها (Authentication / Authorization)
- مدیریت و پردازش پرداخت‌ها، کیف پول و تسویه حساب (Payment / Wallet / Settlement)
- مدیریت سفارش‌ها و محصولات (Order / Product)
- جستجو و سیستم چت (Search / Chat)
- هماهنگی فرآیندها و گردش‌های کار (Workflow / Saga)

بعضی مفاهیم بیزنسی که وجودشون توی کدهای Core نقض معماری به حساب میاد:

- `OrderStatus`
- `PaymentStatus`
- `WalletTransaction`
- `MarketplaceProduct`

## پیامدها

**Consequences**

### مزایا

**Pros**

- تفکیک کاملاً شفاف کارهای فنی و بیزنسی.
- کاهش وابستگی (Coupling) بین سرویس‌ها.
- استانداردسازی نظارت و ثبت رویدادها.
- امکان توسعه و تغییر مستقل سرویس‌های دامنه‌ای.
- افزایش پایداری معماری پلتفرم در بلندمدت.
- امکان تغییر فناوری سرویس‌ها به صورت جداگانه.

### معایب

**Cons**

- اضافه شدن یه سرویس عملیاتی جدید به سیستم.
- نیاز به نگهداری و پایش (Monitoring) مستقل.
- تحمیل هزینه‌های نگهداری لایه پلتفرم (که مدیریت آن به طور رسمی با چارت‌های Helm در شاخه `deploy/` و استقرار بر روی کلاستر K3s/K3d ساده‌سازی می‌شود (D13, D14, D15)).
