## زمینه

**Context**

سرویس Core بخش زیرساختی و مرکزی پلتفرم NONS هستش.
مسئولیت‌های اون شامل دریافت و اعتبارسنجی فنی رویدادها، ثبت لاگ‌های حسابرسی (Audit Logs)، پایش وضعیت سلامت سرویس‌ها و مدیریت Service Registry می‌شه.

چون Core در مسیر عبور تمام رویدادهای سیستم توی NATS قرار داره، نیازمندی‌های فنی مهمی براش داریم:

- **Throughput بالا:** باید بتونه حجم زیادی از رویدادها رو به طور همزمان پردازش کنه.
- **Latency پایین:** نباید تاخیری در انتقال و بررسی رویدادها ایجاد کنه.
- **پایداری طولانی‌مدت:** یه بار ساخته می‌شه و نباید مدام تغییر کنه.
- **مصرف منابع پایین:** باید در کنار بقیه سرویس‌ها با حداقل پردازنده و رم کار کنه.

---

## گزینه‌های بررسی‌شده

**Alternatives Considered**

### گزینه ۱: Node.js/NestJS

**Option 1: Node.js/NestJS**

**دلیل بررسی:** بقیه سرویس‌های پلتفرم با NestJS نوشته می‌شن. اگه از یه ابزار یکسان استفاده می‌کردیم، هزینه یادگیری تیم کمتر می‌شد.

**مشکلات:**

- Node.js به صورت تک‌رشته‌ای (Single-thread) کار می‌کنه و برای کارهای همزمان به Event Loop وابسته هستش که توی بارهای کاری زیاد ممکنه گلوگاه (Bottleneck) بشه.
- مصرف رم بالاتری نسبت به Go داره.
- فریمورک NestJS برای یه سرویس زیرساختی سبک، سنگینه و Overhead اضافی ایجاد می‌کنه.

**نتیجه:** رد شد.

### گزینه ۲: Python

**Option 2: Python**

**دلیل بررسی:** سرویس chat-service با پایتون نوشته می‌شه و تیم باهاش آشنایی داره.

**مشکلات:**

- وجود GIL (Global Interpreter Lock) توی پایتون جلوی پردازش‌های موازی واقعی رو می‌گیره.
- مصرف منابعش واسه یه سرویس همیشه‌روشنِ زیرساختی بالا هستش.

**نتیجه:** رد شد.

### گزینه ۳: Go

**Option 3: Go**

**دلیل بررسی:** زبان Go دقیقاً واسه نوشتن همین مدل سرویس‌های شبکه‌ای با کارایی بالا طراحی شده.

**نتیجه:** ✅ پذیرفته شد.

## دلایل انتخاب Go

**Reasons for Choosing Go**

### ۱. Goroutines برای همزمانی واقعی

**Goroutines for Real Concurrency**

زبان Go از Goroutine استفاده می‌کنه که بسیار سبک‌تر از Threadهای سیستم‌عامل یا Event Loop تک‌رشته‌ای هستن. هر اشتراک در NATS رو می‌شه توی یه Goroutine مستقل اجرا کرد تا هزاران پیام بدون مسدود شدن پردازش بشن.

```go
// هر رویداد در goroutine مستقل پردازش می‌شود
nc.Subscribe("events.>", func(msg *nats.Msg) {
    go func() {
        router.Handle(msg)
    }()
})
```

### ۲. مصرف حافظه پایین

**Low Memory Consumption**

یه سرویس Go در حالت بیکاری (Idle) معمولاً کمتر از ۲۰ مگابایت رم مصرف می‌کنه، در حالی که معادل اون توی Node.js به راحتی بالای ۱۵۰ مگابایت رم می‌خواد. چون Core یه سرویس همیشه‌روشن هستش، این تفاوت در درازمدت خیلی به چشم میاد.

### ۳. کامپایل ایستا و فایل باینری مستقل

**Static Compilation & Independent Binary**

زبان Go یه فایل باینری مستقل تولید می‌کنه که نیاز به هیچ Runtime یا مفسری نداره.

```dockerfile
# Dockerfile نهایی Core
FROM scratch
COPY core /core
ENTRYPOINT ["/core"]
```

با این کار حجم Image نهایی می‌تونه زیر ۲۰ مگابایت باشه که به استقرار سریع‌تر، امنیت بیشتر و استقرار روان‌تر از طریق چارت‌های Helm (D15) بر روی کلاستر K3s/K3d (D13) کمک شایانی می‌کند.

### ۴. استقلال فنی از بقیه سرویس‌ها

**Technical Independence**

اینکه Core با Go نوشته بشه و بقیه سرویس‌ها با Node.js، یه مزیت حساب می‌شه. ارتباط اون‌ها از طریق NATS و در قالب پروتکل هستش و وابستگی به زبان هم ندارن.

### ۵. پایداری بلندمدت

**Long-Term Stability**

زبان Go تعهد خیلی قوی روی سازگاری با نسخه‌های قبلی (Backward Compatibility) داره. Core قراره یه بار نوشته بشه و سال‌ها بدون تغییر اجرا بشه و Go بهترین گزینه واسه این کاره.

---

## آنچه این تصمیم تغییر نمی‌دهد

**Scope Boundaries**

- سرویس‌های بیزنسی همچنان با Node.js/NestJS نوشته می‌شن.
- سرویس چت همچنان با Python توسعه داده می‌شه.
- سرویس Core هیچ منطق کسب‌وکاری نداره و این تصمیم فقط مربوط به تکنولوژی خودِ Core هستش.

---

## پیامدها

**Consequences**

### پیامدهای مثبت

**Positive Consequences**

- کارایی و Throughput فوق‌العاده بالا برای پردازش رویدادها.
- مصرف بسیار پایین منابع سرور.
- فایل باینری سبک و مستقل.
- تفکیک کامل لایه پلتفرم از لایه محصول.

### پیامدهای منفی

**Negative Consequences**

- تیم بک‌اند باید با زبان Go آشنا بشن تا بتونن Core رو نگهداری کنن.
- وجود دو زبان مختلف در کل پروژه، هزینه مدیریت رو یه مقدار بالا می‌بره.

## نتیجه

**Conclusion**

زبان Go برای پیاده‌سازی سرویس Core انتخاب شد. این تصمیم بر اساس نیازهای فنیِ این لایه (همزمانی بالا، تاخیر کم و پایداری) گرفته شده، نه بر اساس ترجیحات شخصی اعضای تیم.
