# بلوپرینت

> **Blueprint v1.0 — سند نهایی**
>
> این سند نمای کلی و یکپارچه از معماری، سرویس‌ها، استانداردها و مسیر توسعه پلتفرم نونز است. برای جزئیات بیشتر به مستندات لینک‌شده مراجعه کنید.

---

## ۱. نمای کلی و اهداف پروژه

**نونز** یک پلتفرم بازارچه توزیع‌شده و رویدادمحور برای بازی است که خریداران و فروشندگان کالاهای دیجیتال بازی — شامل سکه‌های درون‌بازی، کارت‌های هدیه، اکانت‌های بازی، اشتراک‌های پریمیوم و خدمات دیجیتال — را در محیطی امن و مبتنی بر چت به یکدیگر متصل می‌کند. این پلتفرم فراتر از یک بازارچه سنتی عمل کرده و با ادغام ارتباطات بلادرنگ، پرداخت‌های امن با ضمانت، سیستم رقابتی رتبه‌بندی/بازدهی، کشف هوشمند محصول و سامانه داوری و تعدیل با کمک هوش مصنوعی، تجربه‌ای نوین ارائه می‌دهد.

### اهداف اصلی

- ایجاد محیطی امن و مبتنی بر اعتماد که در آن خریداران و فروشندگان بتوانند با اطمینان کامل از طریق سیستم ضمانت واقعی معامله کنند
- ارائه جریان تراکنش مبتنی بر چت بلادرنگ که در آن مذاکره، انجام سفارش و حل اختلاف در یک لایه ارتباطی یکپارچه انجام شود
- ساخت معماری ماژولار و مقیاس‌پذیر با استفاده از اصول **ریزسرویس + رویدادمحور + API-first + سازگار با افزونه**
- فعال‌سازی قابلیت‌های اتوماسیون و یکپارچه‌سازی خارجی از طریق **محرک‌های گردش کار n8n** و وب‌هوک‌ها

---

## ۲. بیان مسئله

بازار ثانویه فعلی بازی از موارد زیر رنج می‌برد:

- عدم اعتماد بین خریداران و فروشندگان
- نبود سیستم ضمانت پرداخت امن
- ارتباط خارج از پلتفرم از طریق دیسکورد/تلگرام
- نبود شفافیت در کیفیت فروشنده
- رقابت ناعادلانه بین فروشندگان
- نبود موتور کشف هوشمند برای پیشنهاد محصول

نونز با ترکیب چت، پرداخت امن، رتبه‌بندی و تعدیل به همه این مسائل رسیدگی می‌کند.

## ۳. محدوده کار

### ۳.۱ هسته اصلی سیستم (موتور رویداد مبتنی بر Go)

هسته مرکزی سبک و بسیار پایدار **رویدادمحور** که به عنوان ستون هماهنگی و مسیریابی عمل می‌کند. این هسته **هیچ منطق تجاری ندارد** و وظایف زیر را بر عهده دارد:

۱. **موتور مسیریابی رویداد** — دریافت، اعتبارسنجی طرحواره، مسیریابی رویدادها با تحویل حداقل یک بار و مدیریت مجدد/شکست
۲. **موتور ماشین حالت** — مدیریت چرخه عمر حالت سفارش (۸ حالت) و اعمال قوانین انتقال
۳. **ثبت خدمات** — ردیابی سرویس‌های فعال، بررسی سلامت، جدول مسیریابی داخلی
۴. **سیستم لاگ حسابرسی** — لاگ رویداد غیرقابل تغییر برای ردیابی کامل، پشتیبانی از اختلافات و پخش مجدد
۵. **لایه اعتبارسنجی رویداد** — تأیید امضا (HMAC/نامتقارن)، اعتبارسنجی طرحواره، جلوگیری از جعل

| مدل              | توضیح                                                                           |

| **تحویل خودکار** | محصول بلافاصله پس از پرداخت در چت تحویل داده می‌شود، بدون نیاز به دخالت فروشنده |

### ۳.۶ جریان اصلی (خرید)

۱. خریدار آرشیو محصولات را مرور می‌کند
۲. خریدار محصول را انتخاب می‌کند
۳. چت با فروشنده باز می‌شود — قیمت به ارز فروشنده مذاکره می‌شود
۴. **تبدیل ارز:** marketplace-service قیمت را از currency-service تبدیل می‌کند — `price_usd_cents` ذخیره می‌شود
۵. سفارش ایجاد می‌شود
۶. پرداخت قفل می‌شود (ضمانت فعال می‌شود)
۷. فروشنده سفارش را تکمیل و تحویل می‌دهد
۸. خریدار تحویل را تأیید می‌کند
۹. وجوه از Escrow به فروشنده آزاد می‌شود
۱۰. **تسویه فروشنده:** settlement-service کمیسیون را کسر و سهم فروشنده را تسویه می‌کند

## ۴. الزامات فنی

### ۴.۱ فلسفه معماری

- **ریزسرویس‌های توزیع‌شده** — با اتصال شل، مقیاس‌پذیر مستقل
- **رویدادمحور** — گذرگاه رویداد به عنوان سیستم عصبی پلتفرم؛ هر تغییری یک رویداد است
- **API-first** — هیچ سرویس داخلی بدون API قابل استفاده نیست؛ هیچ اتصال مستقیمی وجود ندارد
- **سازگار با افزونه** — طراحی ماژولار برای افزودن سرویس‌های بازدهی، رتبه‌بندی، تعدیل هوش مصنوعی به عنوان سرویس‌های قابل الحاق

### ۴.۳ ماشین حالت سفارش

```
CREATED → ACTIVE → COMPLETED
CREATED → CANCELLED
ACTIVE → DISPUTED → COMPLETED | CANCELLED
```

> هر انتقال حالت یک رویداد مستقل است. Order هیچ اطلاعی از Escrow یا Wallet ندارد. برای جزئیات Payment و Wallet به [استاندارد چرخه فروش و تسویه](/docs/team/platform/order-payment-wallet-flow) مراجعه کنید.

### ۴.۴ قرارداد رویداد

```json
{
  "id": "evt_01j2k3m4n5p6q7r8",
  "subject": "nons.order.completed",
  "version": "1.0",
  "timestamp": "2026-06-03T10:54:00.000Z",
  "source": "order-service",
  "traceId": "trace_abc123",
  "payload": {}
}
```

**مفهوم کلیدی:**

- **Event Catalog** = فقط معنی و قرارداد (تعریف ساختار، مالکیت، مصرف‌کنندگان) — [مشاهده کاتالوگ](/docs/team/platform/package/event-catalog)
- **NATS** = فقط حمل‌کننده پیام (پیاده‌سازی فنی انتقال) — [مشاهده استاندارد](/docs/team/platform/standards/event-standard)

**قرارداد نام‌گذاری:** `nons.<domain>.<entity>.<action>` — مثال: `nons.order.completed`

### ۴.۵ معماری امنیتی

| اصل                   | توضیح                                                                                                            |
| --------------------- | ---------------------------------------------------------------------------------------------------------------- |
| احراز هویت جدا        | احراز هویت کاملاً جدا از هسته؛ هسته فقط توکن‌ها را اعتبارسنجی می‌کند                                             |
| ارتباطات امضا شده     | ارتباط سرویس به سرویس با امضاهای دیجیتال                                                                         |
| داده‌های رمزگذاری شده | داده‌های چت و پرداخت در حالت استراحت رمزگذاری می‌شوند                                                            |
| RBAC                  | کنترل دسترسی مبتنی بر نقش در سطح سرویس — [جزئیات](/docs/team/platform/standards/security-policy)                 |
| امنیت ضمانت           | وجوه هرگز مستقیماً لایه برنامه را لمس نمی‌کنند؛ آزادسازی فقط از طریق انتقال‌های حالت اعتبارسنجی شده انجام می‌شود |

### ۴.۶ اصول طراحی

۱. **رویداد = منبع حقیقت** — هیچ حالتی بدون رویداد وجود ندارد؛ هر تغییری یک رویداد است و در لاگ حسابرسی ثبت می‌شود
۲. **استقلال سرویس** — هیچ سرویسی مستقیماً سرویس دیگر را فراخوانی نمی‌کند؛ همه ارتباطات از طریق گذرگاه رویداد انجام می‌شود
۳. **اجرای بدون حالت** — همه سرویس‌ها بدون از دست دادن داده قابل راه‌اندازی مجدد هستند؛ حالت فقط در لاگ رویداد وجود دارد
۴. **ردیابی با طراحی** — هر رویداد از ابتدا تا انتها قابل ردیابی است؛ هر عملی یک مسیر در گراف است

### ۴.۷ محدودیت‌های طراحی هسته

- تأخیر کم در مسیریابی (باید سریع باشد)
- عدم شکست خاموش (باید قابل اعتماد باشد)
- پشتیبانی از پخش مجدد رویداد
- بدون منطق تجاری در هسته
- بدون وابستگی به لایه UI یا کلاینت

### ۷.۴ لایه اتوماسیون (n8n)

**ورودی‌ها:** رویدادهای هسته، وب‌هوک‌های سرویس
**خروجی‌ها:** گردش کار خارجی، APIها، خطوط لوله اتوماسیون

موارد استفاده:

- منطق بازپرداخت خودکار
- خطوط لوله گردش کار تشخیص تقلب
- اتوماسیون اطلاع‌رسانی
- خطوط لوله تحلیل

### ۷.۵ معماری گراف سیستم

```
کلاینت (خریدار/فروشنده/ادمین)
        │
        ▼
   دروازه API (REST / WS / Webhook)
        │
        ▼
   هسته رویداد (Go) — مسیریاب + ماشین حالت + ثبت سرویس
        │
        ▼
   گذرگاه رویداد (NATS JetStream)
        │
        ├── لایه هویت ─────── auth ──── kyc ──── IAM ──── keto
        │
        ├── لایه کسب‌وکار ─── marketplace ─── order ─── payment ─── wallet ─── currency ─── settlement ─── chat
        │
        ├── لایه عملیات ───── dispute ─── zone ─── review ─── moderation
        │
        ├── لایه رشد ──────── boost ─── search
        │
        └── لایه زیرساخت ──── storage ─── notification ─── analytics ─── n8n
```

## ۸. خلاصه

نونز یک **بازارچه بازی بلادرنگ** است که به صورت **گراف رویداد توزیع‌شده** ساخته شده است:

- **هر عملیات = یک رویداد** (غیرقابل تغییر، امضا شده، قابل پخش مجدد، قابل ردیابی)
- **هر سرویس = یک گره** (مستقل، مقیاس‌پذیر، بدون وابستگی مستقیم)
- **هر رویداد = یک یال** (حامل انتقال حالت، قابل حسابرسی)
- **هسته = ستون فقرات مسیریابی و یکپارچگی** (سبک، مبتنی بر Go، بدون منطق تجاری)
- **چت = لایه اجرا** (نه فقط پیام‌رسانی — حالت سفارش + تحویل + تعدیل)
- **n8n = لایه اتوماسیون** (هر رویدادی می‌تواند یک گردش کار خارجی را تحریک کند)
